# SP-02 — does the Host survive the UI's Windows job?

## Question

Spike register SP-02 (ADR-002 D6): does a Node/Electron-spawned child inherit the UI's job object, also when the UI
was started through a Scoop shim? What does starting the Host with `CREATE_BREAKAWAY_FROM_JOB` (a tiny launcher) cost
compared with WMI (latency, console flash, antivirus reaction)?

## Setup

The harness `spikes/SP-02/hostSurvivesJob.os.test.ts` (L8 Windows, `pnpm test:os`) builds the chain from real
processes on one Windows machine:

- A **job holder** creates a job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, starts the **UI** suspended, assigns it to
  the job and resumes it. Three job kinds:
  - `plain`: `KILL_ON_JOB_CLOSE` only (breakaway not allowed, the worst case);
  - `breakaway-ok`: `KILL_ON_JOB_CLOSE | BREAKAWAY_OK`;
  - `scoop-shim`: the job Scoop's `shim.exe` gives the program it starts: `KILL_ON_JOB_CLOSE | SILENT_BREAKAWAY_OK`,
    child created with `CREATE_SUSPENDED`, assigned, resumed, and waited on (read from the shim's own source,
    `kiennq/scoop-better-shimexe` `shim.cpp`, the shim Scoop installs by default).
- The **UI** is a Node process, as Electron main is (same libuv process spawning). It starts the **Host** (a stub that
  serves a named pipe and answers `ping`) by one of two paths:
  - `node-detached`: Node's `spawn(..., { detached: true })`;
  - `d6`: the ADR-002 D6 path: a launcher calling `CreateProcessW` with
    `CREATE_BREAKAWAY_FROM_JOB | CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW` and clean stdio handles (item 1), and,
    when breakaway is refused, WMI `Win32_Process.Create` with a hidden window (item 2).
- The holder then closes the job handle (for the shim, that is the shim ending), and the test asks the Host over its
  pipe. `IsProcessInJob` is recorded for the UI and for the Host before the close.

The job holder, the breakaway launcher, the WMI launcher and the job query are one C# program compiled at test time
by the .NET Framework compiler that ships with Windows (`csc.exe` 4.8). Nothing was installed. The breakaway launcher
stands in for the tiny native launcher D6 item 1 names.

libuv's own code (read from `src/win/process.c`) explains the Node results: `detached` adds
`DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` and deliberately no `CREATE_BREAKAWAY_FROM_JOB`; a non-detached child is
assigned to libuv's own job (`KILL_ON_JOB_CLOSE | BREAKAWAY_OK | SILENT_BREAKAWAY_OK | DIE_ON_UNHANDLED_EXCEPTION`).

## Results

Windows 11 Pro 10.0.26200, three runs (`SP-02/windows-11-measurements.json`). The test runner itself was inside a job
(the agent's shell); `hostInJobBeforeClose: false` means the Host was outside every job.

| UI's job     | Start path      | Launcher used | Host outside every job | Host answers after the job closed | Launch time, whole launcher (ms) | Create call (ms) |
| ------------ | --------------- | ------------- | ---------------------- | --------------------------------- | -------------------------------- | ---------------- |
| plain        | D6              | WMI           | yes                    | yes (3/3)                         | 110–134                          | 46–67 (WMI)      |
| breakaway-ok | D6              | breakaway     | yes                    | yes (3/3)                         | 73–94                            | 20–27            |
| scoop-shim   | D6              | breakaway     | yes                    | yes (3/3)                         | 90–92                            | 24–33            |
| plain        | Node `detached` | —             | no                     | **no** (3/3)                      | 15–17                            | —                |
| breakaway-ok | Node `detached` | —             | no                     | **no** (3/3)                      | 18–22                            | —                |
| scoop-shim   | Node `detached` | —             | yes                    | yes (3/3)                         | 13–22                            | —                |

"Whole launcher" is measured in the UI from spawning the launcher to its exit (it includes starting the .NET launcher
process and, for WMI, the refused breakaway attempt first). "Create call" is measured inside the launcher.

In every chain the UI was in the job and ended when the job closed (`uiExitedWithJob: true`).

## Findings

1. **A Node-spawned Host inherits the UI's job.** With `spawn({ detached: true })` the Host stays in the UI's job and
   dies with it, unless that job grants `SILENT_BREAKAWAY_OK`. Scoop's shim job does, so through the shim a
   Node-spawned Host survives; directly in any other kill-on-close job it does not. ADR-002 D6 item 4 (do not rely on
   Node's spawn) is confirmed by measurement, and `detached` would also bring `DETACHED_PROCESS`, which D6 item 3
   forbids.
2. **Breakaway is refused silently in nested jobs.** The launcher is itself a child of the UI, so libuv puts it into
   libuv's own job, nested inside the UI's job. In the `plain` case `CreateProcessW` with `CREATE_BREAKAWAY_FROM_JOB`
   **succeeded** (no `ERROR_ACCESS_DENIED`), but the Host left only the jobs that allow breakaway and stayed in the
   UI's job, so it died when the job closed (`SP-02/windows-11-breakaway-without-job-check.json`, first entry:
   `launcher: breakaway`, `hostInJobBeforeClose: true`, `hostAnswersAfterClose: false`). The launcher now creates the
   Host suspended, checks `IsProcessInJob`, and treats "still in a job" as refused: it ends the suspended child and
   reports refusal, so the WMI step runs. With that check the Host survived in every job kind.
3. **Cost.** On this machine the breakaway create call took 20–33 ms and the WMI create call 46–67 ms. The whole WMI
   path (refused breakaway, then WMI) took 110–134 ms from the UI. Both stay far below a second.
4. **Console flash and antivirus.** The Host is started with `CREATE_NO_WINDOW` (breakaway) or `ShowWindow = 0`
   (WMI). The agent that ran the spike cannot see the screen, so no visual check was made. Microsoft Defender (default
   configuration) blocked nothing and no run failed, but its protection history was not inspected. Both remain for the
   owner (below).
5. **Not measured here.** The environment block, working directory and parent of a WMI-created Host (it is created by
   the WMI service, not by the UI) were not examined. The launcher issue should check them before relying on
   inherited environment variables.

## Decision

- **The Windows start path stays ADR-002 D6 as written:** the breakaway launcher first (item 1), WMI
  `Win32_Process.Create` when breakaway is refused (item 2). Node's `spawn({ detached: true })` is never the start
  path (item 4). WMI is D6's own second step, exercised and measured here. It is not a replacement.
- **Package detail resolved (consistent with D6 "the Host MUST start outside every job"):** "breakaway refused"
  includes the silent nested-job case. The launcher creates the Host with `CREATE_SUSPENDED`, checks
  `IsProcessInJob`, and on "still in a job" ends the child and falls back to WMI. It resumes the Host only when the
  Host is outside every job. ISSUE-030 (job breakaway) follows this rule, and ISSUE-021 reports
  `hello.jobStatus` from the Host's own `IsProcessInJob` at boot as D6 says.
- The harness stays in the OS lane as the **ADR-002 regression test**: a Host started by the D6 path from a job child,
  directly and through a Scoop-style shim, answers after the job closes, and a job that forbids breakaway forces the
  WMI step.
- Verdict **partial**: the mechanism is measured on Windows 11. What is still missing is the run with an installed
  Scoop `shim.exe` (a stand-in with the same job flags was used), plus the console-flash and antivirus observations.
  The owner steps below close it.

## Owner steps still needed

Run in PowerShell at the repository root, on the maintainer's Windows machine with Scoop installed.

1. Point the harness at an installed Scoop shim. Every `<app>.exe` in Scoop's `shims` folder that has a matching
   `<app>.shim` file is a copy of Scoop's `shim.exe`:

   ```powershell
   pnpm install --frozen-lockfile
   $shim = (Get-ChildItem "$env:USERPROFILE\scoop\shims\*.shim" | Select-Object -First 1).FullName -replace '\.shim$', '.exe'
   $env:SP02_SCOOP_SHIM = $shim
   $env:SP02_REPORT = "spike-results\SP-02\windows-11-real-scoop-shim.json"
   pnpm vitest run --config vitest.os.config.ts spikes/SP-02
   ```

   Expected: `3 passed`, including
   `[SP-02, ADR-002] a Host started from a UI launched through the installed Scoop shim still answers after the shim ends`.
   The JSON gains an entry with `jobKind: "real-scoop-shim"`, `uiInJob: true`, `hostInJobBeforeClose: false` and
   `hostAnswersAfterClose: true`.

2. Watch the screen during step 1. Expected: no console window appears at any point. Then open Windows Security >
   Virus & threat protection > Protection history. Expected: no entry at the time of the run.
3. Scrub and keep the evidence. Check the new JSON for user names or paths (it holds only pids, times and flags).
   Then add the step 1 and 2 observations under "Results" here, set `verdict: passed` if both match the expected
   outcome, and commit:

   ```powershell
   Remove-Item Env:SP02_SCOOP_SHIM, Env:SP02_REPORT
   git add spike-results/SP-02.md spike-results/SP-02/windows-11-real-scoop-shim.json
   git commit -m "docs(spikes): record SP-02 with the installed Scoop shim"
   ```

If step 1 fails (the Host does not answer after the shim ends), the verdict becomes `failed`. The WMI launcher is then
the only start path on Windows, per D6 item 2. Report it to the lead with this record (`25-AGENTS.md` §8.1).

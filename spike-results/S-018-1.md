# S-018-1 — notification from a windowless tray process

## Question

Spike register S-018-1 (ADR-018 item 5, OQ-40 A): can the UI process, running in tray mode with no window open, show
a level-3 notification and receive its click on Windows 11, macOS and the Linux desktops? Which Linux desktops have no
tray? Also: AUMID reuse on Windows, and click activation after the process sat idle.

## Setup

- `spikes/S-018-1/trayApp.cjs`: a throwaway Electron app that never creates a window. It creates a tray icon (an
  in-memory 16 × 16 image), reports `Notification.isSupported()`, sits idle (`S0181_IDLE_MS`), and, by
  `S0181_MODE`, shows no notification (`none`), one unattended notification whose outcome is recorded (`record`), or
  one notification a person clicks (`click`). On Windows it sets the AUMID `DwarfAI.Spike.S0181` before `ready`; on
  macOS it hides the Dock icon (tray only). Every main-process error is printed and ends the process; it cannot open a
  modal.
- `spikes/S-018-1/trayNotification.os.test.ts` (L8): always runs the `none` mode and asserts the windowless tray
  process (tray icon created, zero windows after the idle time, a clean end). In `record` mode (the CI legs, set by
  `.github/workflows/ci.yml`) it also shows one notification on the runner's desktop and records `show`, `failed` or
  a timeout without asserting it, since nobody can click. In `click` mode (the manual guide) it asserts that the click
  reached the tray process with zero windows open. On Linux it records the desktop and asks the session bus whether a
  StatusNotifier watcher (the tray host) and a notification server are present.
- `spikes/S-018-1/linux-desktops.md`: the manual guide (Windows, macOS, one run per Linux desktop).

### CI, unattended (`record` mode), draft PR #1181, run 37073599951

From `S-018-1/<os>-ci-record.json`. No one was there to click, so none of these runs says anything about a click.

| Runner                                            | Tray icon, no window | `isSupported()` | Unattended notification                                    |
| ------------------------------------------------- | -------------------- | --------------- | ---------------------------------------------------------- |
| Windows 10.0.26100, non-elevated CI user          | yes, 0 windows       | `true`          | `show` 7 ms after `show()`; no click, timeout after 15 s   |
| macOS Darwin 25.6.0                               | yes, 0 windows       | `true`          | `failed` after 4 ms: `UNErrorDomain error 1`; then timeout |
| Linux 6.17.0-1022-azure, Xvfb, no desktop session | constructor ok       | `false`         | no event; timeout                                          |

- **Windows:** the windowless tray process shows a toast as a non-elevated user, with the AUMID set before `ready`.
- **macOS:** the tray icon works, but macOS refused the notification. Error code 1 of `UNErrorDomain` is "notifications
  not allowed", read from Apple's UserNotifications error codes and not checked against Apple's documentation here.
  Nobody had allowed notifications for this unsigned Electron on the runner. On a person's Mac the guide has them
  allow "Electron" first. For the packaged app this means the first level-3 notification can fail until the person
  allows notifications, and ISSUE-113 logs that failure (FM-048).
- **Linux:** the runner has no notification server and no tray host. The session bus answered `false` for
  `org.freedesktop.Notifications` and `org.kde.StatusNotifierWatcher`, and `GetServerInformation` failed with
  `ServiceUnknown`. So Electron reported notifications as unsupported, and `new Tray()` succeeded with no tray host to
  draw it. This is a runner without a desktop, **not a verdict on any Linux desktop**. The desktops are the guide's
  step 3.

- **Observed (macOS):** `UNErrorDomain` code 1 is `UNErrorCodeNotificationsNotAllowed`: the authorization was refused

## Decision

- **Until this record says passed on an OS, the gated issues follow the fallback there: level-3 notifications are
  window-only on that OS, and R-16 lists the limit.** ISSUE-112 is unchanged by it (the Host sends level-3 to the
  `notifier` connection either way); ISSUE-113's `ElectronNotificationDisplay` draws only while a window exists on an
  OS where this has not passed; ISSUE-123 records the outcome per OS in `parity-cut-1.md`.
- **Passed on an OS** means: the `click` run of the guide passed there (the click reached the windowless tray process,
  zero windows) and its report is committed under `spike-results/S-018-1/`. The cut-1 entry criterion needs Windows 11
  and macOS (`21` §2 cut 1).
- **Linux**: a desktop passes when its `click` run passes; a desktop whose report shows no StatusNotifier watcher, or
  whose person saw no tray icon, is listed as a desktop without a tray (R-16), and notifications there follow the
  window-only fallback.
- AUMID: the tray process sets the app's AUMID before `ready` (as here); ISSUE-113 reuses the one AUMID the app's
  windows use (`appUserModelId.ts`), so a toast from the tray process and one from a window belong to the same app.

Verdict **partial**. The windowless tray process is measured on Windows, on the three CI runners and, with the npm
Electron, on the owner's Mac. An unattended notification was shown on the Windows runner and refused on the macOS
runner and on the owner's Mac (notifications not allowed, no permission prompt). The macOS `click` run is measured and
**failed** for the npm Electron harness. No click has succeeded on any OS, and no Linux desktop has been measured.
No OS has passed yet, so the window-only fallback holds everywhere, macOS included.

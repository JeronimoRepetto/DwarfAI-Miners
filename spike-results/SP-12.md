# SP-12 — a per-session MCP entry through the protocol, kept out of argv and env

## Question

Spike register SP-12 (ADR-013 item 3; `15` §10 O-15-02): do `codex app-server`, `opencode serve`, `opencode acp` and the
generic ACP driver accept a per-session MCP entry through their protocol without re-serialising it into a child's argv
or env, and which env keys reach the MCP child?

What it gates: `mcpInjection: 'protocol'` for those drivers (ISSUE-152); otherwise the `ticket-file` path-only relay
entry, or `none`. Owner role: provider devs. Issue: ISSUE-325.

## Setup

Real-CLI lane (`17` §4, §5.5). **Run by an agent on the maintainer's Windows 11 machine on 2026-10-17, under a one-off
owner exception to AGENTS.md §0.3, with the owner's own logins and no human at the screen.** No login or logout was
run, no credential file was read, and no auto-approve flag or mode was used (Codex `approvalPolicy: on-request`,
sandbox `read-only`; Kimi ACP mode left at `default`; OpenCode without `--auto`). Every probed process ran with the
agent's own `CLAUDE*` / `CODEX*` variables removed.

The MCP entry is a stand-in relay (a 60-line stdio MCP server, scratch, not committed) whose env holds a random
sentinel, a credential-file path variable and a report path. At start it records its argv, its env key **names** and
whether the spike keys are present. The command line of every descendant of the probed process was read from
`Win32_Process` and searched for the sentinel and the credential path. The scratch probes wrote raw captures in the
`scripts/fixtures/record.mjs` shape in throwaway Git repositories under `%TEMP%`, and each set went through
`node scripts/fixtures/scrub.mjs` (exit 0, no survivors). The committed fixtures were then re-scrubbed with the rules
this change adds to `scripts/fixtures/lib/scrubRules.mjs` (Codex installation id, Claude synced-skill folders, agent
scratchpad folders, percent-encoded home paths, the OpenCode config and Codex MCP status lists).

## Commands

```text
codex app-server                        # stdio JSON-RPC; thread/start with config.mcp_servers.sp12 {command,args,env}
opencode serve --port <port>            # POST /mcp?directory=<repo> {type:'local', command, environment}
opencode acp                            # session/new with mcpServers [{name,command,args,env:[{name,value}]}]
kimi acp                                # the generic ACP stand-in (Kiro is not installed)
```

## Results

Windows 11 Pro 10.0.26200, x64. macOS and Linux: **not run**.

| ---------------------------------- | --------------------------------------------------------------- | ------------------------ | -------------------------------------------------- | ----------------------------------- | -------------------------------------------------------------------------------------- |

- **Not observed: the env of the other descendants.** One Codex turn asked the model to run a `node -e` check of the
  three spike keys in a shell; the Codex Windows sandbox failed to start it (`CreateProcessWithLogonW failed: 267`,
  throwaway repository under `%TEMP%`). Windows does not expose another process's env without debugging it, so only
  the relay's own env was seen, for every driver.
- **Not run:** `claude-agent-acp` and `codex-acp` (not installed), Kiro (not installed).

## Decision

- **The argv half holds** for the four drivers measured: neither the sentinel nor the credential path appeared in the
  command line of any descendant, and nothing was written into a config or project file.
- **The env half is open.** Only the MCP child's own env was observed. Codex scopes it to an allowlist; OpenCode and Kimi
  pass their whole inherited env to it. Whether other descendants receive the entry's keys was not shown.
- **Value ISSUE-152 follows: `mcpInjection` stays `ticket-file`** (the path-only relay entry) for Codex
  `app-server-rpc` and OpenCode `http-server` (whose `POST /mcp` entry is per instance, not per session, in 1.18.32),
  and `opencode acp` and the generic ACP driver stay `none`, until the descendant-env check is run or the owner decides that the
  argv evidence is enough for `protocol`. No driver is set to `protocol` by this record, so `15` §6 C-23 has no
  `protocol` case to follow yet. An open outcome becomes an R-16 known limit at v1.
- **Only Windows ran.** macOS and Linux are not run and are not claimed.

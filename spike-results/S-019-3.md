# S-019-3 — spellcheck dictionary traffic and offline behaviour

## Question

Spike register S-019-3 (ADR-019 item 1, D1; NFR-SEC-11): does Electron 44 download spellcheck dictionaries when
`spellcheck: true`, and does disabling the download URL keep the composer spellcheck working offline? ADR-019 item 1
keeps `spellcheck: false` as the interim value "because it makes no network call", pending the design ruling DG
"composer spellcheck".

What it gates: the composer spellcheck setting (DG) under NFR-SEC-11, the window factory's `spellcheck` value
(ISSUE-046) and the zero-outbound-connections proof of the packaged app (ISSUE-274). Owner role: UI engineer.

## Setup

Two sources:

1. **The packaging spike lane on GitHub-hosted runners**, `.github/workflows/spikes-package.yml`, run 39130693732
   (2026-10-18, `main` at `a222591f`). `spikes/S-019-3/spellcheck.mjs probe` ran `spellcheckProbe.cjs` with the
   repository's Electron in four modes, each in a fresh profile except the last: `off` (`webPreferences.spellcheck`
   false), `on` (true, the default download URL, language `en-US`), `on-unreachable` (true, the download URL set to
   `http://127.0.0.1:9/`), `cached-unreachable` (as `on-unreachable`, reusing the `on` profile). Each run kept a
   Chromium net log. `spellcheck.mjs packaged` started the packaged product (spellcheck off today) for 30 s with a net
   log. No person ran anything.
2. **One local run of the corrected probe** by an agent on a Windows 11 Pro 10.0.26200 machine (OS display language
   `es-AR`, so `en-US` is not an OS language there), 2026-10-18. It runs no product code and touches no DwarfAI data.
3. **A second lane run**, 39134423991 (2026-10-18, `spike/issue-328-records` at `89dd3f09`), same runner images, with
   the corrected probe and the lane fixes: the Windows zip extracted with the system bsdtar, the Linux packaged run
   started from the AppImage. Same four modes and the same 30 s packaged run on each OS.
4. **A third lane run**, 39205769685 (2026-10-19, `main` at `819dd03d`), same images, probe and packaged run.

The probe in run 39130693732 had a defect: its textarea held the misspelled text when the page loaded, and Chromium
marked none of it, so "misspelled word reported" was empty in every mode on every OS, spellcheck on or off. The
corrected probe (this branch) waits until the dictionary is initialized or its download failed, then types the text
(`webContents.insertText`). The local run and run 39134423991 used the corrected probe; the "reported" column of run
39130693732 is therefore not a result, and the table below shows run 39134423991 for the CI runners.

Linux AppImage, Host started, the same two `gvt1.com` dictionary URLs with spellcheck off.

Findings:

- **The download is real on Linux and on a Windows machine without the language.** Chromium fetched
  `/edgedl/chrome/dict/en-us-10-1.bdic` from `redirector.gvt1.com`, which redirected to a `*.gvt1.com` cache. macOS
  and the en-US Windows Server image made no request: they used the OS spellchecker.
- **On Linux, `spellcheck: false` did not prevent the download.** In the `off` mode the window has
  `webPreferences.spellcheck: false` and the probe set no language, yet the default session downloaded the `en-US`
  dictionary at start. ADR-019 item 1's premise for the interim value ("it makes no network call") does not hold for
  the session on Linux in the probe. **The packaged product does the same**: started from the AppImage with
  spellcheck off, it fetched `en-us-10-1.bdic` from `*.gvt1.com` within 30 s (run 39134423991). On Windows Server and
  macOS the packaged product made no request at all.
- **Disabling the download URL keeps the traffic local.** With `setSpellCheckerDictionaryDownloadURL` set to a closed
  local port, the only request on Linux and Windows 11 went to `127.0.0.1`.
- **Offline, spellcheck works only with a dictionary already present.** With the URL disabled and no cached
  dictionary, nothing was reported (Windows 11) and the dictionary never initialized (Linux). With a dictionary cached
  in the profile, spellcheck worked with no traffic (Windows 11).

## Decision

- **The composer keeps `spellcheck: false`** (ADR-019 item 1 interim (a)); turning it on is the design ruling DG's,
  not this spike's.
- **Proposed fallback, for the lead (ISSUE-046 and ISSUE-274):** `spellcheck: false` on the window is not enough to keep
  the Linux session offline in the probe. The package already names the control that is measured to work: ADR-019
  item 1 option (b)'s `session.setSpellCheckerDictionaryDownloadURL` with a URL that cannot be reached. Proposal:
  ISSUE-046's window factory (or the session setup it owns) disables the dictionary download URL on every session,
  whatever the `spellcheck` value, and ISSUE-274's zero-outbound proof asserts no `gvt1.com` request on Linux. The
  packaged Linux capture of run 39134423991 shows the product needs it: today's AppImage downloads the dictionary with
  spellcheck off.
- **For the DG ruling:** option (b) "dictionaries bundled or the download URL disabled" works offline only with a
  dictionary present. With the URL disabled and no bundled dictionary, Windows (without the OS language) and Linux get
  no spellcheck at all; macOS uses the OS spellchecker and made no request.
- **Verdict partial.** Traffic with spellcheck on and off is observed with the corrected probe on the three OSes, the
  packaged product's traffic on the three OSes, and offline behaviour on Windows 11 and Linux. Not yet: the manual
  capture of `spikes/S-019-3/spellcheck-traffic.md` (an outside-the-app capture, which the in-app net log does not
  replace; the register's lane for this spike is "manual with traffic capture", so it is the owner's), and the offline
  case on a Windows or macOS machine that has to download a dictionary. Run 39205769685 on `main` changed none of the
  results above. Whatever is still
  open when v1 is cut is listed as an R-16 known limit by the v1 checklist (later: ISSUE-281).

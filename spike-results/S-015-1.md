# S-015-1 — Codex daemon adopt

## Question

Spike register S-015-1 (ADR-015 item 5; `15` §4.4): can a client re-attach to a running `codex app-server` through the
experimental daemon (socket), instead of `thread/resume` on a stdio server that dies with the Host?

What it gates: Codex `adopt: true` for the `app-server-rpc` driver (ISSUE-152); v1 ships `adopt: false`. Owner role:
provider-integration dev. Issue: ISSUE-325.

## Setup

Real-CLI lane (`17` §4, §5.5), same machine, exception and isolation as `SP-12.md` (Setup), with the owner's own Codex
login (`codex login status`: logged in through ChatGPT). Raw captures in the `record.mjs` shape, scrubbed with
`scripts/fixtures/scrub.mjs` and re-scrubbed with this change's rules.

## Commands

```text
codex app-server daemon version                       # the managed daemon
codex app-server --listen unix://<path>               # AF_UNIX control socket
codex app-server proxy --sock <path>                  # one client per proxy process, raw bytes on stdio
```

Each client sent a WebSocket client handshake and frames through its proxy's stdio, because the control socket expects
a WebSocket upgrade (raw JSON-RPC gives `httparse error: invalid token`).

## Results

Windows 11 Pro 10.0.26200, x64, Codex CLI 0.153.4. macOS and Linux: **not run**.

- **The managed daemon does not exist on Windows.** `codex app-server daemon version` → exit 1,
  `Error: codex app-server daemon lifecycle is only supported on Unix platforms` (`daemon start|stop|restart` and
  `remote-control` alike).
- **A socket-listener adopt works.** `--listen unix://<path>` (a path longer than `SUN_LEN` is refused) plus
  `proxy --sock`. Run 3, the recorded one:
  1. client 1: `thread/start`, turn 1 → "one";
  2. client 3 connected and ran `thread/resume` while client 1 stayed attached → ok;
  3. client 1 was killed (the Host dies) → the server stayed alive, same process;
  4. client 2 (the adopter): `thread/loaded/list` included the thread, `thread/resume` → ok with 1 turn in history,
     turn 2 → "two", `turn/completed`.
- **Earlier runs.** Run 2: `thread/resume` before any turn → `no rollout found for thread id` (a rollout exists only
  after a first turn). Run 1: a second connection opened during the session got no WebSocket upgrade within 60 s; run
  3 did not reproduce it.
- **Side effects.** The listener starts a remote-control task towards the ChatGPT backend and logs the installation id
  and host name (`remoteControl/status/changed` → `disabled`); both are scrubbed. The non-ephemeral threads of runs 2
  and 3 stay as rollouts in the owner's Codex history.

## Decision

- **Failed for the criterion as written**: the daemon is Unix-only in Codex 0.153.4, so no daemon adopt was shown on
  Windows. **v1 keeps `adopt: false`** for the Codex `app-server-rpc` driver (ISSUE-152), which resumes with
  `thread/resume` after a Host restart.
- A socket-listener adopt on Windows was **observed** to work (run 3). Adopting it would change how the Host launches
  Codex (a long-lived listener instead of stdio), which is a later decision, not this record's.
- macOS and Linux daemon: **not run here**. An open outcome becomes an R-16 known limit at v1.

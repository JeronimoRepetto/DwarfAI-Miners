# SP-09 — OpenCode signal for an ask answered in another client

## Question

Spike register SP-09 (ADR-010): does OpenCode reveal, through an event or its pending lists, that a permission or a
question was answered in another client (the OpenCode TUI attached to the same server)? Without it OpenCode reports
`answeredElsewhere: false` (`21` §9 "Cut 2, non-blocking").

## Setup

Real-CLI lane (`17` §5.5) on the maintainer's Mac. `opencode serve` was started on a loopback port and its API was read.
The owner stopped the spike before a TUI was attached: **no ask was raised and no answer was given in any client, on
any OS.** No Windows or Linux run exists.

## Commands

```sh
# opencode serve, bound to 127.0.0.1 on a scratch port
# the API answers 401 without the server's generated password; basic auth with user "opencode" works
curl -u opencode:<generated password> http://127.0.0.1:<port>/openapi.json
```

## Results

Measured: **nothing about answered-elsewhere.** The only observed facts are the API surface of OpenCode 2.0.25
(endpoint discovery, macOS 26.6.2, 2026-10-14):

- `opencode serve` requires authentication: it prints a generated password to its log and the API answers `401`
  without it.
- The API document is `/openapi.json` (`/doc` serves the web UI).
- The event stream is `/api/event`; events have the shape `{id, type, data}`.
- Permission routes: `/api/permission/request` GET, `/api/permission/saved` GET, `/api/permission/saved/{id}` DELETE,
  `/api/session/{sessionID}/permission` POST and GET, `/api/session/{sessionID}/permission/{requestID}` GET,
  `/api/session/{sessionID}/permission/{requestID}/reply` POST with body `{decision: once | always | reject, message?}`.
- There is no question route at this version.
- The pending list before any session was empty.
- There is no `opencode attach` subcommand; a TUI connects with `opencode --server <url> <dir>`.

Not run: an ask answered "Allow once" or "Reject" in the TUI, the event or list change that follows, a late reply after
the TUI answered, and a question answered in the TUI. **No answered-elsewhere signal was observed.**

## Decision

- **Owner waiver (2026-10-14).** The owner approved SP-09 without a measured run:

  > "OpenCode se da por bueno ... doy yo el visto bueno" ("OpenCode is taken as good ... I give my approval").

  Verdict is therefore **passed** on the exit criterion's second branch: `answeredElsewhere: false` is recorded. Not
  run: every answered-elsewhere case, on every OS. This record identifies no signal and commits no OpenCode fixture.

- **OpenCode keeps `answeredElsewhere: false`**, the documented fail-closed default (`21` §9). It is already the value
  of `OPENCODE_CEILING` in `src/host/modules/suppliers/adapters/catalog/profiles.ts`; nothing changes.
- **Gate for ISSUE-136.** ISSUE-136 follows this decision: its broker code stays channel-neutral, and OpenCode asks
  close only by the reconciliation of `15` or the session end, never by an answered-elsewhere signal.
- **The signal is measured before anything relies on it.** The OpenCode resolution signal belongs to EPIC-14
  (ISSUE-229, named by ISSUE-136 "Out of scope"); ISSUE-229 itself says that without SP-09 `answeredElsewhere` is
  `false`. Any issue that wants OpenCode `answeredElsewhere: true` first needs a measured run appended to this record,
  with its event named and its C-12 fixtures under `fixtures/opencode/http-server/<version>/` (`17` §4).

# S-027-1 — the Scoop zip, Scoop's hooks on update and uninstall, and the portable target

## Question

Spike register S-027-1 (ADR-027 D1; ADR-016 item 7; OQ-59): electron-builder 26.15.3's `portable` extraction and the
`zip` target layout for Scoop; whether `pre_uninstall` runs on `scoop update`, and how the hook tells an update from an
uninstall.

What it gates: the Scoop artifact (zip, OQ-33 A), built by ISSUE-275, which has no fallback: if the hook cannot tell
an update from an uninstall, ISSUE-275 stops and reports. Owner role: build engineer.

## Setup

Ran on a GitHub-hosted `windows-latest` runner, packaging spike lane `.github/workflows/spikes-package.yml`, run
39130693732 (2026-10-18, `main` at `a222591f`). No person ran anything. The leg packaged 0.13.1 (`release/`), the same
commit at 0.13.2 (`release-next/`) and electron-builder's `portable` exe (`release-portable/`). The Scoop and portable
parts ran as the standard user `dwarfai-ci` that `scripts/ci/run-unelevated.mjs` creates. Scoop came from its official
installer (`get.scoop.sh`); the zips were served from `127.0.0.1` through a local manifest whose four hooks each log
`$cmd`, `$app`, `$version`, `$global`, `$dir` and the command line (`scripts/ci/packagingSpikes.mjs` `scoopManifest`).

## Decision

- **Zip layout (ISSUE-275).** The release zip holds the app at its root (`DwarfAI-Miners.exe` and `resources/` side by
  side, no top folder), and Scoop installs it as it is: the manifest needs no `extract_dir`. Measured through Scoop's
  own extraction; the entry-list read failed and is re-run with the fixed harness.
- **Portable (OQ-33 B).** The portable exe does not run in place: it extracts itself to `%TEMP%` and runs from there,
  and the Host runs from its versioned copy as on every other layout. OQ-33 B is **not** restored; the Scoop artifact
  stays the zip (OQ-33 A).
- **Hooks (OQ-59), for ISSUE-275.** `$cmd` read `install` in the install hooks and `uninstall` in `pre_uninstall`. What
  `$cmd` reads on `scoop update` is **not yet known**: with the UI running, Scoop skipped the update before any hook.
  ISSUE-275's gate stays closed: its hook must not ship until a run shows the update case.
- **A finding ISSUE-275 must handle.** With the UI (the tray) still running from the Scoop folder, `scoop uninstall`
  ran `pre_uninstall` and only then refused, exiting 0 with the app still installed. A `pre_uninstall` that runs
  `--revert-integrations` would therefore revert integrations and stop the Host on an uninstall that Scoop then
  abandons. Proposal for the lead (unverified): the hook checks for a DwarfAI process still running from `$dir` and
  does nothing in that case, leaving the revert to the uninstall that succeeds; the next lane run measures the
  "UI ended" order. `scoop update` with the tray running also does nothing, so the update notes ask the person to quit
  DwarfAI first.
- **The Host did not start from the Scoop install in this run**, for a reason the evidence does not show (the portable
  exe, on the same runner and user, did start its Host). The harness now saves the product logs before it clears the
  state and records the copy root and the app's processes at the deadline. Until a run shows the Host starting from
  the Scoop layout, ISSUE-275 cannot claim the channel works.
- **Verdict partial.** Layout and portable extraction are recorded; the update/uninstall behaviour with a running Host,
  the exit criterion's core, is not. Whatever is still open when v1 is cut is listed as an R-16 known limit by the v1
  checklist (later: ISSUE-281); for the Scoop hook there is no fallback, so an open hook question blocks the Scoop
  channel rather than shipping a guess.

# S-019-1 — preload under `sandbox: true` on Electron 44

## Question

Spike register S-019-1 (ADR-019 item 1): with the renderer sandboxed on Electron 44, do `contextBridge` and
`ipcRenderer` still work in the preload, and does `webUtils.getPathForFile` still give the path of a dropped file
(composer drag-and-drop attachments), on the three OSes? The answer decides whether cut 0 ships the sandboxed
renderer (`21` §2 cut 0; `parity-cut-0.md`, later: ISSUE-056) and what the window factory follows (later:
ISSUE-046).

## Setup

`spikes/S-019-1/sandboxedPreload.e2e.ts` (L9, the ISSUE-312 harness, `pnpm test:e2e`) launches the built app
(`pnpm build`) under an isolated profile. In the main process (Playwright `evaluate`) it creates hidden test windows
with `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false` and an in-memory session of their own, and
loads a local test page with a file input and a drop zone. Three preloads are tried:

1. the found tree's preload as built, `out/preload/index.mjs` (recorded, not asserted);
2. the same build output transpiled to CommonJS, with nothing else changed (recorded, not asserted);
3. the spike's own minimal facade, `spikes/S-019-1/preload.ts`, compiled to CommonJS at test time (asserted).

For (3) the case asserts, in this order:

- the flag that Electron applied (`getLastWebPreferences().sandbox === true`);
- that the facade loaded (no `preload-error`) and is exposed;
- that the preload reports `process.sandboxed === true` and has no full Node `require`;
- one `ipcRenderer.invoke` round trip to a handler the test registers;
- that a `File` made in the page has no path (`''`);
- the drop itself.

For the drop, a disk-backed `File` is taken from the file input (Playwright `setInputFiles`, file name
`dropped file ñ.txt`) and put into a `DataTransfer`. `dragover` and `drop` events are dispatched on the zone. The page's
drop handler calls `window.spike.pathForFile(file)`, and the path it gets back must be the file's real path.

A drag from the OS file manager cannot be synthesised: the drop carries the same kind of disk-backed `File` a real drop
hands the page, but the OS drag source itself is not exercised.

With the spike facade (Windows):

## Findings

1. **The sandboxed renderer works on Windows and on macOS.** `contextBridge`, `ipcRenderer.invoke` and `webUtils.getPathForFile`
   all work under `sandbox: true` with context isolation and no Node integration. That covers the preload facade and
   the drag-and-drop path the composer needs. On macOS the same case passes with the same expected values.
2. **The preload must be one CommonJS script.** A sandboxed preload is not loaded as an ES module. The found tree
   builds its preload as `out/preload/index.mjs` (the package is `"type": "module"`), so it fails under the sandbox
   today. The same code transpiled to CommonJS loads and exposes `window.api`: its only runtime import is `electron`,
   which a sandboxed preload may `require`. The preload also cannot `require` a sibling chunk, so it has to stay one
   bundled file.
   - **macOS differs on the found preload.** There the current `out/preload/index.mjs` **did** load under
     `sandbox: true` (`foundPreload.preloadError: null`, `bridgeExposed: true`), and so did its CommonJS transpile,
     contrary to what the guide assumed (it expected the ES-module preload not to load). The Windows run above was
     taken at an earlier commit than the macOS run; whether the difference comes from the tree, the build output or
     the OS was not isolated, so it is UNVERIFIED. The condition in the Decision stays: it is the one the Windows
     evidence supports and costs nothing on macOS.
3. **Electron 44 sandboxes by default.** A window created without the `sandbox` option is sandboxed. ADR-019 item 1
   still wants the flag set explicitly by the factory, and the lint rule against `new BrowserWindow(` outside the
   factory is what keeps `sandbox: false` out.

## Decision

- **On Windows the renderer runs sandboxed.** Cut 0 ships the sandboxed renderer (ADR-019 item 1 as written).
  `parity-cut-0.md` records it (later: ISSUE-056), and the window factory keeps `sandbox: true` (later: ISSUE-046).
- **Condition for the gated issues.** The preload that ships with a sandboxed window must be built as a single
  CommonJS file whose only runtime import is `electron` (later: ISSUE-045, the generated facade). An ES-module preload
  does not load sandboxed (finding 2).
- **macOS (2026-10-03):** the sandboxed renderer runs there too, so cut 0's sandboxed renderer holds on Windows and
  macOS.
- **If Linux fails** the owner steps below, the verdict becomes `failed` for that OS. ADR-019 names no
  fallback that turns the sandbox off, so the record then goes to the lead (AGENTS.md §8.1, "a failed spike without a
  usable fallback"). Meanwhile the window factory stays fail-closed with `sandbox: true`
  (`24-issues/README.md` §6).

# S-014-1 — pid source for observed sessions whose files carry no pid

## Question

Spike register S-014-1 (ADR-014 item 2, `15` §5): an observed Codex or Antigravity session (and an OpenCode one, until
verified) records no pid, so DwarfAI cannot end it by identity. Can a process listing, matched by executable, working
folder and start time and identity-checked like ADR-015 item 1, attribute exactly one provider process to one observed
session on Windows, macOS and Linux?

## Setup

- `spikes/S-014-1/pidSource.ts`, the candidate:
  1. List this OS user's processes with pid, parent, start time, executable, command line and working folder: procfs
     on Linux; `ps -A -o pid=,ppid=,lstart=,args=` and `lsof -a -d cwd -Fn` (provider rows only) on macOS; CIM
     `Win32_Process` on Windows, plus the working folder read from each provider row's process parameters (PEB) with
     `NtQueryInformationProcess` and `ReadProcessMemory`, compiled in memory by PowerShell `Add-Type`.
  2. Keep the provider's processes by stem (`codex`, `codex.js`, `codex-<build>`); of a chain of them (a wrapper and
     its native CLI) keep only the root.
  3. Keep the roots in the session's working folder whose start lies within `ATTRIBUTION_WINDOW_MS` (the one shared
     tolerance, `PROCESS_START_TOLERANCE_MS` = 2 000 ms) of the session's first record.
  4. Exactly one → its `ProcessIdentity`. None → `no-identity` (`no-candidate`, or `unreadable` when a root's folder
     or start could not be read). More than one → `no-identity` (`ambiguous`).
- `spikes/S-014-1/pidSource.os.test.ts` (L8): starts stub processes (`stub/codex.cjs`, which writes a Codex-shaped
  `session_meta` line, and the sleeper), lists the real processes and checks five sessions: a wrapper with its
  same-stem child beside a non-provider process (→ the wrapper), a single process (→ it), two processes started
  together in one folder (→ `ambiguous`), a session whose start lies a minute after its folder's process (→
  `no-candidate`), and a folder with no provider process (→ `no-candidate`). Each attributed identity is re-proved by
  the production probe (`NodeProcessControl.probe` + `sameProcess`). Stubs only, never a provider CLI.
- The same file has a real-CLI mode (`S0141_MODE=real`), for the maintainer's machine: the person starts the real CLI
  in a throwaway folder, and the test records the outcome, the provider rows in that folder and the gap between each
  one's start and the session's first record, without asserting it. Never a pid, a path or a name.

- **Windows reads another process's working folder without elevation**, for processes of the same user, through the
  PEB. Node cannot do this, so a production pid source on Windows needs either this PowerShell route (about 0.35 s per
  listing here, once compiled) or a native reader. The native pipe helper already in the repository is the precedent.
- macOS and Linux: the same harness runs in this PR's CI OS lane; its reports are uploaded as `spike-evidence-<os>`
  (`SPIKE_REPORT_DIR`). They are not committed yet.

## Decision

- **Until this record says passed for a provider on an OS, its observed sessions end `failed: 'no-identity'` there:
  nothing is signalled and the mine is kept (ADR-014 item 2, OQ-11 A).** ISSUE-079 builds that outcome and offers
  nothing that depends on a pid source; ISSUE-123 lists the outcome per provider in `parity-cut-1.md`.
- **Passed for a provider on an OS** means: this harness passes on that OS's CI leg, **and** the real-CLI run of that
  provider on that OS (owner guide) reports `identity`, with every provider row in the session's folder started within
  `ATTRIBUTION_WINDOW_MS` of the session's first record. Then ISSUE-079 switches that provider's no-identity test to an
  identity test, and this harness stays as the L8 identity test (TC-319-03).
- **Open risk for the lead.** The rule assumes a CLI writes its session's first record within 2 s of starting. A CLI
  that writes it at the first prompt, or that starts several sessions in one process, puts the gap outside the window,
  and the session stays `no-identity` (fail-closed, never a wrong kill). If the real-CLI gaps show that, the
  alternative to weigh is "the only provider root in the session's folder that started before the first record and is
  still running", which risks attributing a process that belongs to a session not yet written. That needs a lead
  decision. The tolerance itself is the one shared constant and is not widened here.

Verdict **partial**. The candidate is measured on Windows 11 with stub processes only. macOS and Linux run in CI and
are not committed. No real Codex, Antigravity or OpenCode process has been measured.

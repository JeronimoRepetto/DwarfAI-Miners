# S-027-4 — login autostart entry per OS

## Question

Spike register S-027-4 (ADR-027 item 7, AMENDMENT-5, AMENDMENT-6; ADR-002 D4 item 4; ADR-018 D5): which per-user login
entry does each OS use so that the app starts with `--background` at login (tray icon and Host, no window), written
without elevation, read back by `AutostartPort.get()` (present, its command, disabled by the person in the OS's own
startup list), and removed when "Start with the system" is turned OFF?

## Setup

- `spikes/S-027-4/loginEntry.ts`: the candidate entry per OS, under a throwaway name it builds itself (it never reads
  or changes any other entry): Windows, a `REG_SZ` value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`
  through `reg.exe` (`shell: false`), with the person's switch read from `…\Explorer\StartupApproved\Run`; macOS, a
  per-user LaunchAgent in `~/Library/LaunchAgents` read back with `plutil`, "disabled" from
  `launchctl print-disabled gui/<uid>`; Linux, an XDG autostart entry in `$XDG_CONFIG_HOME/autostart` (default
  `~/.config`), disabled by `Hidden=true` or `X-GNOME-Autostart-enabled=false`.
- `spikes/S-027-4/backgroundApp.cjs`: a throwaway Electron app standing in for DwarfAI: it reports whether it got
  `--background`, creates the tray icon a background start shows, opens no window and exits.
- `spikes/S-027-4/loginEntry.os.test.ts` (L8): checks that the process is not elevated, writes the entry, reads it back,
  runs exactly the command the entry stores, removes the entry and reads it back again; a second test switches the entry
  off the way the OS's startup list does (Windows, Linux) and reads it back. CI runs it on the three OSes; the Windows
  CI leg runs as a standard, non-elevated user (`scripts/ci/run-unelevated.mjs`).
- `spikes/S-027-4/loginProbe.ts` and `spikes/S-027-4/clean-vm.md`: the real sign-out and sign-in, per OS.

- **The Desktop-folder prompt is an artifact of where the clone lives.** The clone is under `~/Desktop`, a folder macOS
  protects (TCC); the probe starts Electron from `<repo>/node_modules/...` and writes its marker under
  `<repo>/coverage/...`. That this is the whole cause is probable, not isolated; it is not a property of the login
  mechanism.
- **The `disabledByPerson` reader returns a false negative on macOS 26.** The person turned the row off and the reader
  said `false`. macOS 26 keeps the switch in the Background Task Management (BTM) database, not in the plist (no
  `Disabled` key) and not in `launchctl print-disabled gui/<uid>` (no rows for the probe's label). `sfltool dumpbtm`
  shows, for the entry `8.com.dwarfai.spike.s0274.login-probe`: `Type: legacy agent`,
  `Disposition: [enabled, disallowed, notified] (0x9)`, `Parent Identifier: Unknown Developer`. Also, after the switch
  was turned off, `launchctl print gui/<uid>/com.dwarfai.spike.s0274.login-probe` answered `Could not find service`
  while the plist was still present. A reliable reader on macOS would have to read the BTM disposition (`disallowed`)
  or, indirectly, the absence of the service in launchd with the plist present. Neither reader was written or measured
  here.
- **`remove` leaves a stale BTM record.** Right after `remove`, `sfltool dumpbtm` still listed
  `8.com.dwarfai.spike.s0274.login-probe` although the plist no longer existed, even though the row left the settings
  list. Whether the stale record matters, or clears later, was not measured.

## Findings

1. **Windows: the per-user `Run` value meets every scripted part**: written and removed without elevation, read back
   exactly, and the person's switch in Settings → Apps → Startup is readable from `StartupApproved\Run` (an odd first
   byte means off; the format is undocumented by Microsoft, so the real-login check confirms it with a real switch).
2. **The candidate autostart does not start the app with `--background`.** Today's `src/main/shell/autostart.ts`
   registers the packaged app with no arguments, so a login start opens the app as a normal launch. ISSUE-060 evaluates
   the candidate; the gap is recorded for it.
3. **The candidate Linux entry misses one escaping layer.** `src/main/platform/autostartEntries.ts` quotes `Exec`
   arguments but does not apply the string-value escaping the Desktop Entry Specification applies first, so a launch
   path holding a backslash would be read back differently. The spike's writer and reader apply both layers.
4. **macOS: the real login works, and the person's switch is not readable the way the spike reads it.** The
   LaunchAgent started the app with `--background`, opened no window and created the tray icon, and `remove` took the
   row out. But `launchctl print-disabled` (the spike's "disabled" source) does not hold the person's switch on
   macOS 26: it lives in the BTM database.

## Decision

- **Chosen entry per OS (the candidate, to be confirmed at a real login):** Windows, the per-user `Run` value (not a
  Startup-folder shortcut: the value is written and read back with `reg.exe`, and the person's switch is readable);
  macOS, a per-user LaunchAgent; Linux, an XDG autostart entry. Each points at the channel's stable launch path with
  `--background` (ADR-027 item 7).
- **Until this record says passed on an OS, ISSUE-060 keeps `LOGIN_ENTRY_PASSED` false there** (its
  `loginEntryGate.ts`): the candidate autostart stays the one writer of the login entry on that OS until v1, and the
  rebuilt entry lands before v1 (`21` §4 row "Login autostart entry"; `20` P-09, R-11). ISSUE-061 follows the same gate
  for Reset metrics, and ISSUE-123 records the outcome per OS in `parity-cut-1.md`.
- **macOS is not passed (2026-10-03).** `check` printed `CHECK PASSED`, but the second half of the definition below,
  the person's switch read back, is a false negative there (`disabledByPerson: false` with the row off). So
  `LOGIN_ENTRY_PASSED` stays false on macOS until a reader based on the BTM disposition (or on the launchd service
  being absent) is measured and its read-back committed.
- **Passed on an OS** (for the cut-1 gate) means: the OS-lane harness passed on that OS, and the real-login check of
  `clean-vm.md` printed `CHECK PASSED` there with its report and the person's switch read-back committed under
  `spike-results/S-027-4/`. Then ISSUE-060 sets `LOGIN_ENTRY_PASSED[<os>]` to true and switches that OS's candidate
  writer off in the same change.
- **The packaged-channel questions** (survival across `scoop update`, an `nsis` upgrade, an AppImage move and a macOS
  app move; antivirus or SmartScreen on the unsigned build; removal by every uninstall) need the real packaged app
  writing its own entry, which ISSUE-060 builds. They are not part of the cut-1 gate and are re-checked on packaged
  builds by ISSUE-328 before v1.

Verdict **partial**: the scripted half passed on Windows (this machine and the CI runner), macOS and Linux (CI). The
real sign-out and sign-in is recorded on macOS only: it started the entry and removed it, but the person's switch
read-back failed, so macOS has not passed. No OS has passed: `LOGIN_ENTRY_PASSED` stays false everywhere. The packaged
channels belong to ISSUE-328.

# S-027-3 — the per-user installer and uninstaller against a running Host

## Question

Spike register S-027-3 (ADR-027 D1; ADR-016 item 7; ADR-002; OQ-59): the `nsis` installer's running-app check and its
uninstaller against a Host running from the versioned copy, and the upgrade flag (`isUpdated` / `--updated`,
UNVERIFIED) the old uninstaller receives during an upgrade.

What it gates: the downloadable installer channel, built by ISSUE-276, which has no fallback: if the installer kills
or blocks on the Host, ISSUE-276 stops and reports. Owner role: build engineer.

## Setup

Ran on a GitHub-hosted `windows-latest` runner, packaging spike lane `.github/workflows/spikes-package.yml`, run
39130693732 (2026-10-18, `main` at `a222591f`), as the standard user `dwarfai-ci` that
`scripts/ci/run-unelevated.mjs` creates (the Host refuses to start elevated, ADR-002 D6). No person ran anything. The
harness `spikes/S-027-3/installerVsHost.mjs` installs the 0.13.1 setup silently, starts the installed app, upgrades to
0.13.2 with the Host running, starts the upgraded app and uninstalls, watching every process each step starts.

A second run, 39134423991 (2026-10-18, `spike/issue-328-records` at `89dd3f09`, same image), ran the whole sequence
with the fixed harness (install folder taken from the uninstaller, UI ended before the upgrade and the uninstall,
product logs saved).

A third run, 39205769685 (2026-10-19, `workflow_dispatch` on `main` at `819dd03d`, same image), ran the same sequence
with the harness that also records the upgraded UI's exit and the processes under the install folder.

## Decision

- **For ISSUE-276:** the per-user installer installs silently without elevation to `%LOCALAPPDATA%\Programs\dwarfai-miners`
  and writes no `InstallLocation`; anything that needs the install folder reads it from the uninstall string's
  folder. Its running-app check looks only at processes whose path is under the install folder, so a Host running
  from `%LOCALAPPDATA%\DwarfAI\host\<version>` is outside what it checks (read from the command line it ran, and
  confirmed against a running Host in run 39134423991).
- **Upgrade against a running Host (run 39134423991):** the per-user upgrade neither kills nor blocks on a Host running
  from its copy, and the old uninstaller receives `--updated` (with `/KEEP_APP_DATA` and `--keep-shortcuts`), so
  ISSUE-276's uninstall hook can tell an upgrade from a removal by `--updated`.
- **Removal against a running Host (run 39134423991):** the uninstaller neither kills nor blocks on the Host, and the
  Host keeps running after the app is gone, with its copy and the app data left. For ISSUE-276: the removal path
  (its `--revert-integrations` hook, without `--updated`) is the only place that can stop the Host and remove
  `host\<version>`; nothing in the stock uninstaller does.
- **Not measured yet:** the ADR-002 D8 handshake after the upgrade, and `--revert-integrations` on an upgrade and a
  removal, which needs the hook ISSUE-276 builds. Run 39205769685 repeated the upgrade and removal results above on
  `main`, and narrowed the handshake gap: the upgraded 0.13.2 UI starts, exits with code 0 on its own, and logs nothing.
  So it does not crash and is not blocked by the installer, but it never reaches the launcher's `versioned-copy` step.
  Finding the cause is agent and CI work (a harness or product investigation, then a new lane run), not an owner step.
- **ISSUE-276's gate stays closed**: it builds and tests its hooks, and merges only after a lane run records its hooks on
  an upgrade and a removal with a running Host, and the upgraded app's handshake. **Verdict partial.** Whatever is still open when v1 is cut is listed as an
  R-16 known limit by the v1 checklist (later: ISSUE-281); for the installer there is no fallback, so an open upgrade
  question blocks the installer channel rather than shipping a guess.

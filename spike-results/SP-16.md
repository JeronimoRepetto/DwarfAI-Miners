# SP-16 — the OS secret-store library for the Host

## Question

Spike register SP-16 (ADR-017 item 2; ADR-002; `05` §3.12, R11): for the `@napi-rs/keyring` candidate, its license and
maintenance, prebuilt N-API binaries per OS and architecture, loading under `ELECTRON_RUN_AS_NODE` from the versioned
copy, Linux without Secret Service, and macOS Keychain prompts across versioned copies and unsigned builds.

What it gates: the `OsKeyringSecretStore` adapter and R11's containment path, and the step 3a entry for the one-time
Jev key migration (`21` §9). The step 4a entry expects it already passed. Owner role: host dev. Issue: ISSUE-322.

## Setup

One probe script, run three times on the maintainer's Windows 11 machine. **It was run by an agent with the owner's
approval on 2026-10-16, with no human at the screen.** The probe is a scratch tool of the owner runbook and is not
committed. It uses only Node built-ins plus the library under test. It touches only Credential Manager entries under
the service `dwarfai-sp16-probe`, which hold random test values that are never printed, and it deletes them before it
ends. It reads no other credential.

- The library was installed with the owner's permission into a scratch folder under `%TEMP%` only, not into the
  repository: `pnpm add @napi-rs/keyring@2.1.0 --save-exact` (exit 0, `+ @napi-rs/keyring 2.1.0`). pnpm resolved the
  Windows binding `@napi-rs/keyring-win32-x64-msvc` 2.1.0 (`keyring.win32-x64-msvc.node`). pnpm noted that 2.1.1 is
  available, and the pin stays 2.1.0.
- Run 1: plain Node 24.
- Run 2: the repository's Electron binary with `ELECTRON_RUN_AS_NODE=1`, the way the Host runs (ADR-002 D1).
- Run 3: the same Electron run, loading the library from a copied folder, where the library and its Windows binary
  are plain folders with no link, as a packaged app or the Host's versioned copy holds them (SP-03).

License, redistribution and pinning of the library are in `S-008-1.md` (MIT, owner decision 2026-10-16: bundle,
pinned exactly).

The macOS and Linux rows, and a second Windows row, come from the hosted-runner spike lane (`docs/spikes-lane.md`):
the committed harness `spikes/SP-16/keyringUnderElectron.os.test.ts` runs `spikes/SP-16/keyringProbe.cjs` in the
repository's Electron 44.0.0 binary under `ELECTRON_RUN_AS_NODE=1`, once from the installed runtime and once from a copy
of it (the whole `Electron.app` bundle on macOS, symlinks kept). Every entry sits under a service unique to the run
(`DwarfAI-Miners.sp16-<random>`), with random values that are never printed, and is deleted before the probe ends. The
same job runs the adapter's own OS tests (`src/host/modules/preferences/adapters/secret-store/*.os.test.ts`).

## Decision

- **The candidate passes.** `@napi-rs/keyring` 2.1.0 sets, reads, lists and deletes an entry in Windows Credential
  Manager, the macOS Keychain and the Linux Secret Service, under Electron 44 with `ELECTRON_RUN_AS_NODE=1`, from the
  installed runtime and from a copy of it. Its license is recorded in `S-008-1.md`, with the owner's bundle decision.
- **The library the real adapter uses is `@napi-rs/keyring`, pinned exactly at 2.1.0**, imported only inside
  `preferences/adapters/secret-store/**` (R11; TC-322-03). No fallback library is chosen (TC-322-02 applies only to a
  failed candidate).
- **Linux without a Secret Service (the open item of the Windows run), settled.** Measured on the runner: an entry the
  library is not told where to store **is stored anyway** (the library's own fallback, the kernel keyring), while an
  entry pinned to the Secret Service is refused with `Platform failure`. So the adapter pins every Linux entry to the
  Secret Service and reads that refusal as `unavailable` (ADR-017 item 5), which `napiKeyringBinding.ts` does and the
  adapter's `[C-23, FM-115]` OS test passed on the runner. There is no plain-text or kernel-keyring fallback.
- **Waiver (2026-10-18).** The owner ruled:

  > "if it can't be tested here, take it as good"

  It applies only where the issue names a default or a fallback. ISSUE-322 does: if the candidate fails, another
  library or a small native module implements the same port (TC-322-02, ADR-017 item 2), and ADR-017 item 5 keeps
  `unavailable` with no plain-text store. The rows taken as good under it, not run and not done:
  1. the Keychain prompt with a person's login keychain, when a newer build (different bytes) or the unsigned app reads
     an entry an older build wrote (needs a person at a Mac; the runner measured byte-identical copies only);
  2. the prebuilt binaries on the architectures the runners do not have (macOS x64, Linux arm64), which the lockfile
     pins at 2.1.0 (`S-008-1.md`);
  3. the library loaded from inside a packaged build's `app.asar.unpacked` (this lane loads it from `node_modules`).

- **Verdict passed**: every register check is measured on Windows, macOS and Linux (with and without a Secret Service),
  or taken as good under the waiver above. Before this run the verdict was **partial** (Windows only).
- **What it unblocks:** the ISSUE-217 gate (the one-time Jev key migration, step 3a entry, `21` §9) and the step 4a
  entry that expects SP-16 passed.

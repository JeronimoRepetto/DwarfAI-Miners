# S-030-1 — detecting case-insensitive volumes cheaply

## Question

Spike register S-030-1 (ADR-030 item 1, `normalizePathKey`): how does the Host tell, cheaply, whether the file system
of a mine's folder compares names without case, so that mine identity folds case only where the file system does?
macOS and Linux are the question; Windows is the control.

## Method (the candidate)

`spikes/S-030-1/caseFolding.ts`, `detectVolumeCase(realPath)`: take the nearest component of the real path whose name
has a cased letter, swap the case of that name, and stat both spellings in the same parent directory. The same file
(device and inode, read with `bigint: true`) means the directory holding that name folds case; a missing or different
file means it does not. A path with no cased letter in any component, or one that cannot be read, answers `unknown`.
It writes nothing and spawns nothing: two `stat` calls. It is the probe `src/host/platform/endpoint/nodeEndpointEnv.ts`
already uses for `hostDataDir` on macOS, with `bigint` identities.

## Setup

`spikes/S-030-1/caseFolding.os.test.ts` (L8, `pnpm test:os`) builds, with no person involved, one folder whose file
system folds case and one whose file system does not, and runs the method twenty times on each:

| OS      | Folds case (expected `case-insensitive`)                        | Does not fold (expected `case-sensitive`)                                          |
| ------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Windows | NTFS temp folder                                                | NTFS temp folder with the per-directory case-sensitive flag (`fsutil`, unelevated) |
| macOS   | disk image `APFS` (`hdiutil`, unelevated)                       | disk image `Case-sensitive APFS` (`hdiutil`, unelevated)                           |
| Linux   | ext4 `casefold` image, folder with `+F` (loop mount, `sudo -n`) | the same image, folder without `+F`; fallbacks: a FAT image, a plain ext4 image    |

The OS's own temp folder is measured as an observation. The Linux leg relies on the CI runner's passwordless `sudo`;
`sudo -n` never prompts, so a machine without it fails fast with a clear message. CI runs the harness on
`windows-latest`, `macos-latest` and `ubuntu-latest` on every pull request, and uploads the reports as the artifact
`spike-evidence-<os>` (`.github/workflows/ci.yml`, step "Upload spike evidence").

## Findings

1. **The method is cheap**: two `stat` calls, a median of about 0.1 ms on NTFS, no write and no spawn.
2. **Windows does not fold every folder.** A folder with the per-directory case-sensitive flag (set by `fsutil` without
   elevation here; WSL is said to set it on folders it creates, UNVERIFIED here) compares names exactly, and the method
   sees it. ADR-030 item 1 and
   ISSUE-064's `volumeCase.ts` fold every Windows path, which would give two folders differing only in case one mine
   key on such a volume. This contradicts an assumption of the package; it is reported to the lead here and not acted on.
3. **Identities must be read as `bigint`.** An NTFS file index is 64-bit and loses precision as a JavaScript number;
   `nodeEndpointEnv.ts` reads numbers, which is safe only on macOS, where it runs.
4. **Folding is per directory on Linux** (ext4 `casefold` is the `+F` attribute of a directory), so the answer belongs
   to the directory that holds the probed name, not to a whole volume. The Linux CI leg measures both on one volume.
5. On a folding NTFS folder, `realpathSync.native` of a wrongly cased spelling returns the on-disk spelling, so two
   spellings of one folder already resolve to one real path there.

## Decision

- **The detection method is the candidate above** (case-swapped `stat` of the nearest cased component, `bigint`
  device and inode, `unknown` when there is nothing to probe or the path cannot be read). Its answer is cached per
  directory that holds the probed name, not per device, because Linux folds per directory (finding 4).
- **Until this record says passed on an OS, the gated issues follow the fallback there: no case folding on unknown
  volumes** (`21` §2 cut 1). ISSUE-062 keeps taking the fold decision as an input (`caseFoldFor`: Windows folds,
  `unknown` never folds), ISSUE-063 stores what it is given, and ISSUE-064's `volumeCase.ts` answers `unknown` on macOS
  and Linux. ISSUE-123 records this in `parity-cut-1.md`.
- **Passed on macOS or Linux** means: that OS's CI leg ran this harness with both kinds of folder prepared and the
  method matching both, and its report is committed under `spike-results/S-030-1/`. Then ISSUE-064 replaces `unknown`
  on that OS with this method, and nothing else changes.
- Finding 2 (Windows case-sensitive folders) goes to the lead; until the lead decides, ADR-030 item 1 is followed as
  written on Windows.

Verdict **partial**: the method is chosen and measured on Windows (the control). The macOS and Linux measurements are
produced by CI and not yet recorded.

# S-030-1 — detecting case-insensitive volumes cheaply

## Question

Spike register S-030-1 (ADR-030 item 1, `normalizePathKey`): how does the Host tell, cheaply, whether the file system
of a mine's folder compares names without case, so that mine identity folds case only where the file system does?
macOS and Linux are the question; Windows is the control.

## Method (the candidate)

`spikes/S-030-1/caseFolding.ts`, `detectVolumeCase(realPath)`: take the nearest component of the real path whose name
has a cased letter, swap the case of that name, and stat both spellings in the same parent directory. The same file
(device and inode, read with `bigint: true`) means the directory holding that name folds case; a missing or different
file means it does not. A path with no cased letter in any component, or one that cannot be read, answers `unknown`.
It writes nothing and spawns nothing: two `stat` calls. It is the probe `src/host/platform/endpoint/nodeEndpointEnv.ts`
already uses for `hostDataDir` on macOS, with `bigint` identities.

## Setup

`spikes/S-030-1/caseFolding.os.test.ts` (L8, `pnpm test:os`) builds, with no person involved, one folder whose file
system folds case and one whose file system does not, and runs the method twenty times on each:

| OS      | Folds case (expected `case-insensitive`)                        | Does not fold (expected `case-sensitive`)                                          |
| ------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Windows | NTFS temp folder                                                | NTFS temp folder with the per-directory case-sensitive flag (`fsutil`, unelevated) |
| macOS   | disk image `APFS` (`hdiutil`, unelevated)                       | disk image `Case-sensitive APFS` (`hdiutil`, unelevated)                           |
| Linux   | ext4 `casefold` image, folder with `+F` (loop mount, `sudo -n`) | the same image, folder without `+F`; fallbacks: a FAT image, a plain ext4 image    |

The OS's own temp folder is measured as an observation. The Linux leg relies on the CI runner's passwordless `sudo`;
`sudo -n` never prompts, so a machine without it fails fast with a clear message. CI runs the harness on
`windows-latest`, `macos-latest` and `ubuntu-latest` on every pull request, and uploads the reports as the artifact
`spike-evidence-<os>` (`.github/workflows/ci.yml`, step "Upload spike evidence").

## Findings

1. **The method is cheap**: two `stat` calls, a median of 0.09 to 0.15 ms on every OS, no write and no spawn.
2. **Windows does not fold every folder.** A folder with the per-directory case-sensitive flag (set by `fsutil` without
   elevation, here and on the CI runner; WSL is said to set it on folders it creates, UNVERIFIED here) compares names
   exactly, and the method sees it. ADR-030 item 1 says Windows folds case, and ISSUE-062 and ISSUE-064 fold every
   Windows path. On such a folder, that would give two folders that differ only in case one mine key.
3. **Identities must be read as `bigint`.** An NTFS file index is 64-bit and loses precision as a JavaScript number;
   `nodeEndpointEnv.ts` reads numbers, which is safe only on macOS, where it runs.
4. **Folding is per directory on Linux** (ext4 `casefold` is the `+F` attribute of a directory). The CI leg had a
   folding and a non-folding folder on one volume, and the method told them apart. So the answer belongs to the
   directory that holds the probed name, not to a device.
5. **The real path does not settle the spelling everywhere.** On NTFS and APFS, `realpathSync.native` of a wrongly cased
   spelling returns the on-disk spelling, so two spellings already resolve to one real path. On a Linux casefold folder it
   returns the spelling it was given. Only the case fold of the key merges the two spellings there.

## Decision

- **The detection method is the candidate above**: a case-swapped `stat` of the nearest cased component, with `bigint`
  device and inode. It answers `case-insensitive`, `case-sensitive` or `unknown`. It answers `unknown` when no component
  has a cased letter or the path cannot be read.
- **Fold a mine key only where the detection says its folder folds.** The probe runs on the mine folder's real path.
  Its answer belongs to the directory that holds the probed name, and is cached per that directory's real path, never
  per device. The cache may share the resolver's lifetime (ADR-030 item 2, 30 s); the probe costs two `stat` calls, so
  no longer cache is needed.
- **Windows follows the same rule, per directory** (finding 2). An NTFS folder folds by default; a folder with the
  per-directory case-sensitive flag does not. This departs from ADR-030 item 1's wording "case-folded on Windows", and
  the lead must record it in ADR-030. The change only stops folding where the file system does not fold.
- **`unknown` never folds: no case folding on unknown volumes.** This keeps the conservative default of `21` §2 cut 1
  for the paths the method cannot probe.
- What ISSUE-062, ISSUE-063 and ISSUE-064 change to follow this decision is listed below. ISSUE-123 records in
  `parity-cut-1.md` that S-030-1 passed.
- Known limit, accepted: the key is folded as a whole. A non-folding ancestor whose name differs only in case above a
  folding mine folder could merge two mines. That needs case-sensitive and case-folding directories nested on purpose.

Verdict **passed**: the method is chosen, and it is measured on a folding and a non-folding folder on Windows (the
control, on two machines), macOS and Linux, with the OS versions above (NTFS, APFS, ext4 casefold).

## What the gated issues change to follow this record

- **ISSUE-064** (`src/host/modules/mines/adapters/volumeCase.ts`):
  - `volumeRulesFor` stops answering a constant per OS: no `'case-insensitive'` for every Windows path, no `'unknown'`
    on macOS and Linux;
  - on all three OSes, `volumeCase(realPath)` runs this detection on the real path and returns its answer, with
    `bigint` identities and the per-directory cache above;
  - its `volumeCase.os.test.ts` drops the "no key is folded until S-030-1 passes" expectation. It asserts the folding
    and non-folding folders of this harness instead (APFS and case-sensitive APFS images on macOS; ext4 casefold `+F`
    and plain folders on Linux; NTFS and a case-flagged folder on Windows), citing `[S-030-1]`.
- **ISSUE-062** (`src/host/modules/mines/domain/minePath.ts`):
  - `caseFoldFor(style, volume)` becomes `volume === 'case-insensitive'`: Windows no longer folds regardless of the
    answer, and `unknown` still never folds;
  - its tests that expect a Windows path to fold with `unknown` or `case-sensitive` change, with this record as the
    reason.
  - `PathStyle` still decides separators only.
- **ISSUE-063**: no rule of its own changes. It stores the key it is given, and picks up ISSUE-062's `caseFoldFor`
  through the branch it builds on. Any fixture that assumes every Windows key is folded changes with ISSUE-062's.
- Outside these issues, noted for the lead and not changed here: `nodeEndpointEnv.ts` reads `number` identities
  (finding 3), and its comment "Linux volumes are case-sensitive" is contradicted by finding 4. The Linux endpoint rule
  takes no case input, so nothing breaks there.

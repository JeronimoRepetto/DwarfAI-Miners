# SP-03 (S-027-2) — size and time of the Host's versioned copy per packaged layout

## Question

Spike register SP-03, alias S-027-2 (ADR-002 D5; ADR-027 item 2): how large is the versioned copy of the app runtime,
and how long does it take, on first start from each packaged layout (the Scoop zip of the unpacked app, the `nsis`
install directory, the AppImage, the `.app`)? After the copy, does the AppImage runtime copied out of its FUSE mount
still start the Host once the mount is gone? Does the copy of a notarized, hardened `.app` keep its signature without
triggering Gatekeeper again?

## Setup

`spikes/SP-03/versionedCopy.os.test.ts` (L8, `pnpm test:os`, one leg per OS) runs the copy as ADR-002 D5 writes it:

1. build the manifest of the unpacked app directory (every file and symlink, with its SHA-256). In production this
   is `host-manifest.json`, generated at build time, so this cost is reported apart;
2. copy the directory to `host/<version>.tmp-<pid>` (`fs.cpSync`, symlinks kept verbatim, timestamps kept);
3. verify the copy against the manifest;
4. rename it atomically to `host/<version>`;
5. start again: the verified copy is found and reused;
6. start the copied executable under `ELECTRON_RUN_AS_NODE=1` (how the Host runs, ADR-002 D1). The probe script
   reports its `execPath`, the Electron version and, where the layout has one, the `name` read from `app.asar`;
7. read the bundle's signature state before and after the copy: Authenticode status on Windows, `codesign --verify
--deep --strict` and `spctl --assess --type execute` on macOS, the executable mode on Linux.

A third case tampers with a source file after its manifest was built: the copy must fail verification, be removed and
never be renamed into place. That is the seed of the ADR-027 copy-atomic test.

Two measurement rules came from the first CI run of the harness (PR #1084):

- **Windows signature read.** The harness starts Windows PowerShell 5.1 by its `System32` path, without `PSModulePath`.
  On `windows-latest`, the step shell is PowerShell 7, and its module path, inherited by the 5.1 child, made
  `Get-AuthenticodeSignature` fail with `CouldNotAutoloadMatchingModule`. That diagnosis is inferred from the error;
  it was not reproduced on this machine, which has no PowerShell 7. A read that still fails is reported as
  `authenticode:unreadable(<reason>)`, and the case fails on that named result, not on an exception.
- **Running from the copy.** "Runs from the copy" compares real paths. On macOS the temp directory `/var/folders/…` is a
  symlink to `/private/var/folders/…`, and the Host reports the resolved `execPath`. The first comparison used
  unresolved paths and failed on `macos-latest`: a harness defect, reproduced here with a directory link. Each
  measurement now carries `diagnostics` (the `execPath` the Host reported and the copied path, both relative to the
  work directory, and whether the work directory is a link), so the macOS CI leg shows which paths were compared.

The layouts measured on Windows:

- `electron-dist-win32`: the Electron 44 runtime the repository installs (`node_modules/electron/dist`), the same files
  electron-builder packs around the app. The OS lane measures it on every run, on every OS.
- `app-win-unpacked`: the real app's unpacked directory from one throw-away build,
  `pnpm build && pnpm exec electron-builder --win dir --x64 --publish never -c.directories.output=<tmp>
-c.win.signAndEditExecutable=false`. Nothing was signed or published, and the build was deleted afterwards. Its
  files are the ones the Scoop zip holds (ADR-027 D1, OQ-33 A: the zip of the unpacked app) and the ones the `nsis`
  installer writes to its install directory.

On both layouts the copied Host started under `ELECTRON_RUN_AS_NODE` (Electron 44.0.0), and its `execPath` was
inside the copy, not the source. In the app layout it read `dwarfai-miners` from the copy's `app.asar`. No
`.tmp-<pid>` directory was left behind, and the second start reused the verified copy. The tamper case threw
"does not match the manifest", left nothing renamed into place, and removed the temp copy.

Other observations:

- **The first start of a freshly written executable can be slow.** The first start from the `electron-dist-win32`
  copy took 2 285 ms in this run and 178 ms in an earlier run. The app layout, whose executable has the same bytes,
  then started in 63 ms. The likely cause is the antivirus scanning a new binary on first start (UNVERIFIED: not
  isolated here).
- **Today's app carries 209 MiB that the rebuild removes.** `resources/app.asar.unpacked/node_modules/@anthropic-ai/
claude-agent-sdk-win32-x64` is 209 MiB of the 685 MiB. ADR-008 item 1 takes the Claude Agent SDK out of the product,
  so the rebuilt app's copy should be about 480 MiB (an estimate, not measured).
- **The reuse check re-hashes the whole copy** (193–364 ms per start here). ADR-002 D5 says only that "an existing,
  verified copy is reused". How often the copy is re-verified is ISSUE-031's choice, and this is an input to it, not a
  decision.
- **Byte copies keep the Authenticode state.** Neither executable is signed: the Electron binary from npm is not, and
  the app has no Windows signing configured. The Authenticode status is part of the file bytes, so a byte-exact,
  manifest-verified copy keeps it by construction. A signed build can confirm this when one exists.

## Decision

The copy rule of ADR-002 D5 and ADR-027 item 2 **is confirmed as written** for the layouts measured. The copy source
is the running app's unpacked application directory. It is copied to `<version>.tmp-<pid>`, verified against the
manifest, renamed atomically, and reused once verified. ISSUE-031 follows this table:

| Layout                                        | Copy rule                                                                                                                    | Evidence                                                                                                                                                         |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Windows, Scoop zip (unpacked app)             | as written: copy the directory holding `process.execPath` and `resources`                                                    | measured, `app-win-unpacked`: 685 MiB, 1.5 s copy, 0.5 s verify, Host starts from the copy                                                                       |
| Windows, `nsis` install directory             | as written: same source directory, same files                                                                                | same files as the unpacked app; a run from a real install is owner step 3                                                                                        |
| Windows, Electron runtime (any layout)        | as written                                                                                                                   | measured, `electron-dist-win32`, and on every OS-lane run                                                                                                        |
| macOS, unsigned `.app` (installed soak build) | as written: copy the whole `.app` bundle with symlinks kept verbatim                                                         | measured, `app-mac` and `electron-dist-darwin`: 589 MiB and 286 MiB, 0.3 s and 0.1 s copy, Host starts from the copy, signature state identical before and after |
| macOS, signed and notarized `.app`            | as written, provisionally: copy the whole `.app` bundle with symlinks kept verbatim; confirmed only when owner step 1 passes | pending: `codesign` and `spctl` before and after on a notarized build (owner step 1)                                                                             |
| Linux, AppImage                               | as written: copy the runtime out of the `--appimage-mount` mount, start it after the mount is gone                           | measured on a hosted Ubuntu 24.04 runner (run 39136245328): 614 MiB, 0.2 s copy, 0.5 s verify, mount gone before the Host started, Host starts from the copy     |
| Linux, deb (`/opt` install)                   | as written                                                                                                                   | measured on a hosted Ubuntu 24.04 runner (run 39136245328): 612 MiB, 0.2 s copy, 0.5 s verify, Host starts from the copy                                         |

If owner step 1 shows that the copied `.app` loses its signature or is assessed again by Gatekeeper, the verdict
becomes `failed` for macOS. The alternative copy source to name then is the one the register asks for: ISSUE-031 must
not run the Host from a plain file copy of the bundle, and the record goes to the lead with the measured state
(AGENTS.md §8.1). The same applies to the AppImage if the copied runtime does not start once the mount is gone. The
spike does not pick a replacement in advance.

Verdict **partial**: Windows and unsigned macOS are measured. The AppImage and deb layouts still need a Linux machine,
and the signed and notarized `.app` needs the owner's signing identity and notarization, so the exit criterion (the
`.app` and AppImage copies keep signature and Gatekeeper state) is not met on every layout yet.

Findings of this run:

- **The rule works on the Windows zip and `nsis` layouts**, as on the macOS and Linux ones: copy on first start, Host
  from the copy, Host outlives the UI, second start reuses the copy. The Windows copy is 705 MiB (739 689 022 bytes).
- **A source directory reached through a junction or symbolic link is not copied.** Scoop installs into
  `apps\<app>\<version>\` and starts the app through `apps\<app>\current`, a directory junction to it. The UI's source
  directory (the folder of `process.execPath`) is then the junction, and `versionedCopy.ts`'s `nodeCopyOps.copyTree`
  calls `fs.cp(from, to, { recursive: true, verbatimSymlinks: true, … })`: with the source root a link and no
  `dereference`, Node copies the link, not the tree. The "copy" is a link to the install folder, which also holds
  Scoop's `scoop-install.json` and `scoop-manifest.json`, so the manifest check finds extra entries and fails
  (`MANIFEST_MISMATCH`), and no Host starts. Reproduced on an agent machine with Node 24.11.1: `fs.cp` from a junction
  with the same options produced a symbolic link listing the junction target's extra file. Had the check passed, the
  copy would still have pointed into Scoop's folder, which `scoop update` removes. The fix belongs to the launcher
  (copy from the real path of the source directory, for example `fs.realpath` of it before the copy), not to this spike;
  it gates the Scoop channel (S-027-1, ISSUE-275) and the copy rule of ISSUE-270.
- **AppImage mount.** The mount outlives the UI, but nothing under it is held by the Host or any other process, so the
  copy rule's claim (the Host does not depend on the mount) holds. Why the mount itself was still listed (FUSE
  teardown timing on the runner) is not known and does not change the rule.
- **Unsigned macOS copy.** The copied bundle has the same signature state as the source (`adhoc`, invalid, Gatekeeper
  rejected), as the OS lane recorded on 2026-10-03. The signed and notarized case still needs the owner.

The verdict stays **partial**: the signed and notarized `.app` needs the owner, and the Scoop layout fails on a
launcher defect that this record names but does not fix. The copy rule table under "Decision" is unchanged; the Linux

source directory resolved to its real path. What is still open for v1 is listed as an R-16 known limit by the v1
checklist (later: ISSUE-281) unless a later run closes it.

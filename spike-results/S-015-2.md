# S-015-2 — boot and logon identity per OS

## Question

Spike register S-015-2 (ADR-015 item 4, OQ-55, AMENDMENT-3; `13` FM-110; `09` §8.4). On Windows 11 (Fast Startup on and
off, restart, update reboot, sign-out), on macOS, and on Linux (systemd or not, logind or not):

- which of the item 4 sources (`bootId`, `bootTimeMs`, `logonSessionId`) can the Host read under
  `ELECTRON_RUN_AS_NODE`, without elevation?
- how stable is each one within one boot?
- does each one change across a reboot and across a logout?

It also asks whether a faster Windows source than `Win32_OperatingSystem.LastBootUpTime` exists without new
dependencies. ISSUE-018 had measured that query at 0.4–0.5 s warm, and above the 2 000 ms bound of `16` §2.6 when
cold.

## Setup

The procedure and the list of candidate sources are in `spikes/S-015-2/bootIdentity.md`. The scripted half is
`spikes/S-015-2/bootIdentity.os.test.ts` (L8, `pnpm test:os`, one leg per OS). It reads every candidate five times,
asserts that the sources item 4 names are readable and stable, records the latencies, and checks rules 1–4 on each kind
of transition. The reader, `spikes/S-015-2/bootIdentity.ts`, was also run once under Electron 44 with
`ELECTRON_RUN_AS_NODE=1`, the way the Host runs. Identity values are stored as SHA-256 prefixes (privacy guard).

## Results

Windows 11 Pro 10.0.26200.9457, Fast Startup **on** (`HiberbootEnabled = 1`, read, not changed). The full table is
in `bootIdentity.md`, "Observed on Windows 11". In short:

| Source                                          | Readable, no elevation (Node / Electron RunAsNode) | Stable in the run | Latency           |
| ----------------------------------------------- | -------------------------------------------------- | ----------------- | ----------------- |
| registry `PrefetchParameters\BootId`, `reg.exe` | yes / yes                                          | yes (counter 213) | 23–110 ms         |
| CIM `LastBootUpTime`, PowerShell (as written)   | yes / yes                                          | yes               | 413–704 ms (warm) |
| `now − os.uptime()` = `now − GetTickCount64()`  | yes / yes                                          | yes               | 0.1 ms            |
| token `AuthenticationId` LUID (as written)      | only through native code (reference helper)        | yes               | —                 |
| logon SID, `whoami.exe /logonid`                | yes / yes                                          | yes               | 41–122 ms         |

- The three boot instants disagree: the tick-based one is 16 s before CIM `LastBootUpTime` and 18 s before the
  kernel's `BootTime`. Each one was stable within the run.
- `now − QueryUnbiasedInterruptTime()` sits 31.8 h after the others, which is the machine's accumulated sleep. It is
  never a boot identity.
- The logon SID is not the `AuthenticationId` LUID, but both belong to the same logon session.

The transitions (restart, hybrid and full shutdown, sign-out, update reboot, sleep, a day of uptime) have **not** run
yet: each one ends the session that would run the script, and some need the owner's own restarts. They are owner steps
W1–W7 below. macOS and Linux have not run here.

## Findings

1. **CIM `LastBootUpTime` costs 0.4–0.8 s warm**, and ISSUE-018 saw a cold read above 2 000 ms. ISSUE-018 (PR #1077,
   merged) handles this by reading it once, when the adapter is constructed: an in-flight read is shared and a failed
   read is retried, all within the frozen `BOOT_ID_QUERY_TIMEOUT_MS = 2 000` (`16` §2.6). So the latency does not
   fall on each boot-identity comparison.
2. **Two sources would give one machine two boot ids.** The tick-based instant (`now − os.uptime()`, identical to
   `now − GetTickCount64()`) is 16 s before CIM `LastBootUpTime` here, and 18 s before the kernel's `BootTime`. Every
   reader of the Windows boot id (the process identities of ISSUE-018, `currentBootIdentity()` of ISSUE-019) must
   therefore use one and the same source, or no recorded process would ever match. A tick-based instant also follows
   the wall clock and can flip at a second boundary when it is rounded. It is not used as `bootId`.
3. **The registry `BootId` counter is a fast, clock-free candidate for `bootId`.** It is readable without elevation
   through `reg.exe`, which ships with Windows (23–110 ms). It is undocumented, and whether it changes on a restart, a
   full shutdown and a hybrid (Fast Startup) shutdown is UNVERIFIED (owner steps W1–W3).
4. **The Windows `logonSessionId` as written cannot be read from Node.** `TokenStatistics.AuthenticationId` needs
   `GetTokenInformation`, and the Host has no native module (no new dependency). The token's logon SID is the
   per-logon identifier Node can reach, through `whoami.exe /logonid` (ships with Windows, 41–122 ms). Rule 2 depends
   on it to catch a Fast Startup shutdown, which does not change the boot. Whether it changes on sign-out and after a
   hybrid shutdown is owner steps W2 and W4.

## Decision

- **Until the lead records the table, ADR-015 item 4 is used as written, with every decision logged**
  (`host.boot.rebooted`, `19` §9.1). For the ProcessControl adapter (later: ISSUE-019, following ISSUE-018), "as
  written" means these choices within item 4:
  - **Windows `bootId` and `bootTimeMs`:** CIM `Win32_OperatingSystem.LastBootUpTime` rounded to the second, which is
    ADR-015 item 4's first source. ISSUE-018 implements it, and ISSUE-019 reuses the same readers for
    `currentBootIdentity()`, so both derive the boot id identically (finding 2). Its latency (413–704 ms warm here) is
    handled by the read at adapter construction, within the 2 000 ms bound (finding 1). `now − os.uptime()` is not
    used for the boot id.
  - **Windows `logonSessionId`:** the token's logon SID from `whoami.exe /logonid` (spawned with `shell: false`,
    lint R17). This resolves a package detail gap: the LUID the table names is unreadable without native code, and the
    logon SID identifies the same token's logon session. `'unknown'` when the spawn fails.
  - **Linux and macOS:** the sources item 4 names, each `'unknown'` when unreadable.
- **Proposed correction for the lead:** the table below. It becomes the table of item 4 only after owner steps W1–W7
  and P0–P3 confirm it and the lead records it (ADR-015 is not edited here).

## Proposed table for ADR-015 item 4

| OS      | `bootId`                                                                                                                                                                                   | `bootTimeMs`                                                                           | `logonSessionId`                                                                                                              | Status                                                                            |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Windows | **proposed, not adopted:** registry `HKLM\…\Memory Management\PrefetchParameters` `BootId` via `reg.exe`, a fast exact counter (adopted today: CIM `LastBootUpTime` rounded to the second) | CIM `LastBootUpTime` rounded to the second (as written and as ISSUE-018 implements it) | the token's logon SID via `whoami.exe /logonid` (was: `AuthenticationId` LUID, unreadable from Node)                          | readable and stable on 10.0.26200; transitions pending (W1–W7)                    |
| macOS   | `sysctl kern.bootsessionuuid` (as written)                                                                                                                                                 | `sysctl kern.boottime` (as written)                                                    | `SECURITYSESSIONID` from the environment (was: `getaudit_addr`, which Node cannot call); otherwise `'unknown'`                | pending (P0–P3; the OS lane leg reads the `bootId` and `bootTimeMs` sources)      |
| Linux   | `/proc/sys/kernel/random/boot_id` (as written)                                                                                                                                             | `/proc/stat` `btime` (was: `now − os.uptime()`; `btime` is the kernel's own instant)   | logind session (`XDG_SESSION_ID`, or the cgroup `session-N.scope`), otherwise `/proc/self/sessionid`; `'unknown'` when absent | pending (P0–P3, with and without systemd/logind; the OS lane leg reads `boot_id`) |

If W1–W3 show that `BootId` does not change across a restart or a full shutdown, the proposal is withdrawn and the Windows `bootId`
stays CIM `LastBootUpTime` rounded to the second. If they show that it does, adopting it is the lead's decision, and it
would replace the CIM source in every reader at once (ISSUE-018 and ISSUE-019), never in only one. If W2 shows that the logon SID
does not change after a hybrid shutdown, rule 2 cannot catch Fast Startup, and the record goes to the lead: no
fallback is documented for that case (AGENTS.md §8.1).

Verdict **partial**: readability, latency and stability within one run are measured on Windows. The transitions, and
macOS and Linux, are owner steps.

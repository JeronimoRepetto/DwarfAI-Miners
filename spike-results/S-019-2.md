# S-019-2 — which Electron fuses electron-builder 26.15 sets per target

## Question

Spike register S-019-2 (ADR-019 item 5): which fuses `electron-builder` 26.15 can flip per build target, and asar
integrity on the Linux AppImage. ADR-019 item 5 asks for `EnableNodeOptionsEnvironmentVariable=false`,
`EnableNodeCliInspectArguments=false`, `EnableCookieEncryption=true`, `OnlyLoadAppFromAsar=true`,
`EnableEmbeddedAsarIntegrityValidation=true` (where supported per OS), with `RunAsNode` kept on because the Host runs
the app executable with `ELECTRON_RUN_AS_NODE` (ADR-002).

What it gates: ISSUE-269 (flip the fuses at package time) and the v1 checklist (ISSUE-281). Owner role: build
engineer.

## Setup

Ran on GitHub-hosted runners, packaging spike lane `.github/workflows/spikes-package.yml`, run 39130693732
(2026-10-18, `workflow_dispatch` on `main` at `a222591f`), one leg per OS: `windows-latest`, `macos-15` (unsigned,
`-c.mac.identity=null`) and `ubuntu-latest`. No person ran anything; the record was written by an agent from the
uploaded evidence.

Each leg packaged the release targets twice from the same commit: once as `ci.yml`'s `package` job does (`release/`),
and once with the ADR-019 item 5 set asked of electron-builder through its `electronFuses` option
(`spikes/S-019-2/electron-builder.fused.cjs`, into `release-fused/`). `spikes/_packaged/extract.mjs` extracted every
artifact with the OS's own tools, and `spikes/S-019-2/fuses.packaged.mjs` read the fuse wire of the executable (or of
`Electron Framework` on macOS) and the asar integrity record of every unpacked app and every extracted artifact.

The fuse wire has the same layout on every target (version 1, nine fuses). `e` is enabled, `d` disabled. Columns:
RunAsNode, EnableCookieEncryption, EnableNodeOptionsEnvironmentVariable, EnableNodeCliInspectArguments,
EnableEmbeddedAsarIntegrityValidation, OnlyLoadAppFromAsar.

- **Today's release build differs from ADR-019 item 5 on five fuses, on every OS**: cookie encryption off,
  `NODE_OPTIONS` and the inspect arguments allowed, asar integrity validation off, loading outside the asar allowed.
  Only `RunAsNode` (on) matches. Flipping them is ISSUE-269's work.
- **electron-builder 26.15.3 sets the whole ADR-019 set** on macOS (both arches, zip and dmg) and Linux (deb and
  AppImage): every fused artifact reads exactly the recorded set.
- **Asar integrity on Linux.** No Linux artifact carries an integrity record, with or without the fuse set, while
  every macOS artifact carries one in `Info.plist` that matches the asar header. The fuse
  `EnableEmbeddedAsarIntegrityValidation` is on in the fused Linux builds, but with no record there is nothing for it
  to check. This run did not test whether a tampered asar is refused on any OS.
- **Windows: not measured for the fused build.** The fused build was packaged (the step succeeded), but the step that
  reads it starts with the extraction, which failed on the zip: in the workflow's bash step, `tar` is Git's GNU tar,
  which read `D:\...` as a remote host (`tar: Cannot connect to D: resolve failed`) and cannot read a zip anyway. The
  same failure kept the release zip out of the release read. Reproduced on an agent machine with Git Bash; the system
  bsdtar (`%SystemRoot%\System32\tar.exe`) lists the same kind of zip. Fixed in this branch
  (`scripts/ci/packagingSpikes.mjs` `tarCommand`).
- **Whether the fused build still starts its Host was not tested.** `RunAsNode` stays on, but `OnlyLoadAppFromAsar`
  and asar integrity change what the executable will load. The lane now starts the fused build once per OS with the
  SP-03 harness (step "S-019-2 the build with the ADR-019 set starts its Host", evidence `S-019-2/start/`).

## Decision

- **The recorded fuse set per target, for ISSUE-269's `scripts/release/fuses.expected.json`:** macOS and Linux take
  the full ADR-019 item 5 set (`RunAsNode` on, cookie encryption on, `NODE_OPTIONS` and inspect arguments off,
  `OnlyLoadAppFromAsar` on, embedded asar integrity validation on), set through electron-builder's `electronFuses`.
  It is verified on the wire of every macOS and Linux artifact of the release targets.
- **Linux has no embedded asar integrity record.** ISSUE-269 lists asar integrity on Linux as a known limit of the
  shipped Linux targets (TC-269-02), whatever the fuse says.
- **Windows is not yet verified.** Until a re-dispatch of the lane reads the fused Windows build, ISSUE-269 follows its
  own fallback for Windows: flip what each target is proven to support, here nothing beyond today's set, and list the
  rest as known limits. ISSUE-269 merges only after this record says what Windows supports.
- **Verdict partial.** The fuse set is recorded and verified for macOS and Linux; Windows and the "fused build starts
  its Host" check are not. Whatever is still open when v1 is cut is listed as an R-16 known limit by the v1 checklist
  (later: ISSUE-281).

# S-011-1 — the meaning of `on-verified` for the OpenCode plugin

> **Finding for ISSUE-229 (plugin ask channel): in OpenCode 1.18.32 the project plugin's `permission.ask` hook was
> not called for an `edit` ask.** The ask reached only the HTTP API (`GET /permission`, answered with
> `POST /permission/{id}/reply`) and the event stream (`permission.asked` → `permission.replied`). Observed once, on a
> person-run server (fixture `s0111-person-run-deny*`). An ask channel that relies on that hook would never see this
> ask; ISSUE-229 must read asks from the HTTP API and the event stream, or show that the hook fires in its own case.

## Question

Spike register S-011-1 (ADR-011 items 2, 7; ADR-016 item 5): is a plugin file written just before a launch loaded by
the next Host-launched `opencode serve`, and by a person-run server without a restart? Does OpenCode signal that the
plugin is loaded? Is OpenCode's launch-time deny setting honoured?

What it gates: the meaning of `on-verified` ("written and read back" until then) for the toggle (ISSUE-228), the plugin
ask channel (ISSUE-229) and the 4a switch (ISSUE-235); the OpenCode row of ADR-011 item 2. Owner role: provider dev
(OpenCode). Issue: ISSUE-327.

## Setup

Real-CLI lane (`17` §4, §5.5), same machine, exception and isolation as `SP-12.md` (Setup). The probe plugin is a
zero-import `.opencode/plugin/sp-probe.js` that appends a marker line (with the process id) when it is initialised;
in the person-run deny run it also records any `permission.ask` call, and changes nothing.

Server kinds:

- **Host-launched**: an `opencode serve` started after the plugin file was written.
- **Person-run**: an `opencode serve` that was already running when the plugin file was written.

Runs:

1. **Host-launched, load and deny**, and **person-run, load**: with the owner's own OpenCode setup.
2. **Person-run, deny** (a second owner-authorized run the same day): `opencode serve` started as its own detached
   process from a folder that is not the project, as a person starts it. The global config was isolated with
   `XDG_CONFIG_HOME=<temp dir>`, so none of the owner's global plugins or MCP servers loaded (`GET /mcp` → `[]`,
   `/config.plugin` lists only the probe); the data directory holding the login was untouched. With the server already
   running, the project got `.opencode/plugin/sp-probe.js` and `opencode.json` with
   `permission: {edit: ask, bash: ask, webfetch: deny}`; only then was the project opened, by its first `?directory=`
   request. One turn asked the agent to create `deny-probe.txt`.

## Commands

```text
opencode serve --port <port> --print-logs
GET  /config?directory=<repo>                        # lists the file under plugin
GET  /event                                          # plugin.added and permission.* events
POST /session ... prompt_async                       # first directory-scoped request
POST /instance/dispose                               # person-run load case only
OPENCODE_CONFIG_CONTENT={"permission":{"edit":"deny","bash":"deny","webfetch":"deny"}}   # Host-launched deny case
XDG_CONFIG_HOME=<temp dir> opencode serve --port <port> --hostname 127.0.0.1 --print-logs   # person-run deny case
GET  /permission                                     # the pending ask
POST /permission/{id}/reply {"reply":"reject"}       # the deny
```

## Results

Windows 11 Pro 10.0.26200, x64, OpenCode 1.18.32. macOS and Linux: **not run**.

| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1.18.32, Host-launched | loaded at the first directory-scoped request; the marker's process id is the server's                                                                                                                                                             | **none**: `GET /config` lists the file under `plugin` (discovery, not proof of loading); the `plugin.added` events name only built-in ids; the `--print-logs` INFO lines have no plugin line | honoured: `/config.permission` shows the setting; asked to write a file, the agent had no write, edit or bash tool, the file was not created, and no `permission.*` event came (one turn)                                                                                                                     |

- **The plugin's `permission.ask` hook was not called** for the person-run ask (0 calls recorded, observed once); see
  the finding at the top.
- Side effects of run 1: the session ran with the owner's global OpenCode setup, whose global plugins include the old
  app's permission plugin and whose MCP servers include a memory server. The agent called that server and wrote one
  memory row to the owner's store. Run 2 wrote none (isolated config, no MCP servers). The sessions of every probe
  stay in the owner's OpenCode history.

## Decision

- **`on-verified` means "written and read back"** for ISSUE-228 and ISSUE-229 (ADR-011 item 2): no loaded signal was
  identified in OpenCode 1.18.32, for either server kind.
- **For a person-run server, written-and-read-back does not imply loaded** for a project that server already opened:
  it needs a server restart. The plugin loads when the project is opened after the write. The toggle and the ask
  channel must not claim that the plugin is active for an already-open project; ADR-011 item 7's card rule while
  `on-verified` applies.
- **The deny is verified for both server kinds**: the launch-time setting (`OPENCODE_CONFIG_CONTENT` permission deny)
  on a Host-launched server, and a rejected ask through `POST /permission/{id}/reply` on a person-run server.
- **ISSUE-229 must not rely on the plugin's `permission.ask` hook** in OpenCode 1.18.32: the ask reached only the HTTP
  API and the event stream.
- **Verdict passed** for OpenCode 1.18.32: the load behaviour, the loaded signal (its absence) and the deny are
  recorded with fixtures for both server kinds. Only Windows ran; macOS and Linux are not run and are not claimed.

# S-031-1 — Codex TUI attach to an app-server-owned thread

## Question

Spike register S-031-1 (ADR-031 D1): can a Codex TUI attach to a thread owned by the Host's `codex app-server` without
becoming a second writer?

What it gates: `console: 'attach'` for launched Codex (ISSUE-170); `log` until then. Owner role: driver engineer.
Issue: ISSUE-325.

## Setup

Real-CLI lane (`17` §4, §5.5), the same machine, exception and run as `S-015-1.md` (run 3). No TUI was started: that
needs a terminal and a person at the screen ("not observed: no human at the screen").

## Commands

```text
codex --help                    # lists --remote <ws://…|unix://PATH>
codex agents --help             # codex agents --remote
```

The attach itself was measured as a second protocol client of the same listener, which is what a `--remote` TUI is
(`S-015-1.md`, run 3).

## Results

Windows 11 Pro 10.0.26200, x64, Codex CLI 0.153.4. macOS and Linux: **not run**.

- `codex --remote <ws://…|unix://PATH>` and `codex agents --remote` exist in 0.153.4.
- A second client attached while the owner client was attached. It received the whole live turn of the other client
  (`turn/started`, `item/*`, `item/agentMessage/delta`, `turn/completed`) and could resume the thread.
- **Nothing in the protocol makes such a client read-only**: any attached client can `turn/start`.
- Not observed: the TUI itself, and whether the TUI writes unprompted.

## Decision

- **Failed**: no attach without a second writer was shown. **`console: 'log'` stays** for launched Codex (ISSUE-170).
- An open outcome becomes an R-16 known limit at v1. macOS and Linux: not run here.

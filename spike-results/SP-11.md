# SP-11 — a Claude Code hook that returns a permission decision

## Question

Spike register SP-11 (ADR-012 item 1): per OS and Claude Code version, (a) does Claude Code honour an `allow` / `deny`
returned by a hook for its permission dialog, (b) can the person still answer the same dialog in the terminal while
the hook waits, with a late hook decision ignored, (c) does a hook timeout fall back to Claude's own dialog, never to
allow, and (d) can DwarfAI tell from hook or transcript evidence that the dialog was answered, and by whom?

## Setup

Real-CLI lane (`17` §5.5) on the maintainer's Mac, with the maintainer's own Claude Code login and the owner at the
keyboard. A scratch project outside the repository; the repository clone was not changed (same commit, zero changed
files, before and after). No auto-approve flag; `--permission-mode default` in every case.

A small scratch hook script (`decide` mode returns the case's decision after the case's delay; `log` mode only records)
was loaded with `--settings` in three variants:

- **P**: `PermissionRequest` runs the hook in `decide` mode; `PreToolUse`, `PostToolUse`, `Notification` and `Stop`
  in `log` mode.
- **P10**: P with a 10 s hook timeout on `PermissionRequest`.
- **T**: `PreToolUse` runs the hook in `decide` mode.

Each case asked Claude to run one harmless command (`touch` of a marker file) or to ask one `AskUserQuestion`. The
marker file's presence shows whether the tool ran. User and plugin hooks of the machine were active on other events
only (`Notification`, `UserPromptSubmit`, `SessionStart`, `Stop`, `SubagentStop`, `SessionEnd`), never on
`PreToolUse`, `PermissionRequest` or `PostToolUse`.

## Commands

```sh
# per case: set the decision and delay, then start Claude with the case's settings variant
node sp11-hook.mjs set-case <case> allow|deny|none|exit1|answer <delayMs>
claude --permission-mode default --settings sp11-settings-<P|P10|T>.json
```

| Case | Variant | Hook reply      | Purpose                                    |
| ---- | ------- | --------------- | ------------------------------------------ |
| A1   | P       | `allow` at once | (a) allow honoured                         |
| A2   | P       | `deny` at once  | (a) deny honoured                          |
| B1   | P       | `allow` at 40 s | (b) terminal No while the hook waits       |
| B2   | P       | `deny` at 40 s  | (b) terminal Yes while the hook waits      |
| C1   | P10     | `allow` at 30 s | (c) timeout at 10 s                        |
| C2   | P       | no decision     | (c) no decision                            |
| C3   | P       | exit 1          | (c) hook error                             |
| E1   | P       | no decision     | item 5: `PermissionRequest` for a question |
| T1   | T       | `allow` at once | (a) on `PreToolUse`                        |
| T2   | T       | `allow` at 20 s | (b) on `PreToolUse`                        |
| E2   | T       | answer at once  | item 5: `PreToolUse` answering a question  |

## Results

macOS 26.6.2 (25G83) arm64, Claude Code 2.1.299, 2026-10-14. The per-criterion table, with every case, is

| Criterion | `PermissionRequest`                    | `PreToolUse`              |
| --------- | -------------------------------------- | ------------------------- |
| (a)       | passed (A1, A2)                        | passed (T1)               |
| (b)       | passed (B1, B2)                        | failed (T2)               |
| (c)       | passed (C1, C2, C3)                    | not measured              |
| (d)       | informational: transcript, not payload | informational: transcript |

## Findings

1. **`PermissionRequest` is the only candidate route.** It meets (a), (b) and (c) on this OS and version. A returned
   decision takes effect at once; the dialog stays answerable while the hook waits; a timeout, a missing decision and a
   hook error all leave Claude's own dialog, and nothing was ever allowed by them.
2. **`PreToolUse` fails (b).** While a `PreToolUse` hook waits there is no dialog, so the person cannot answer in the
   terminal. It is rejected by ADR-012's own options table ("blocking hook without parallel terminal answering").
3. **B2 asymmetry.** After a terminal No, Claude sends `SIGTERM` to the waiting `PermissionRequest` hook. After a
   terminal Yes, it does not: the hook keeps running and writes its late decision after the turn has ended. Claude
   ignored it (no visible effect), so (b) holds. But a hook shim that forwards its pending call to the Host is not told
   that the terminal answered first, so the Host cannot close the ask `answered-elsewhere` (ADR-012 item 2) from the
   hook alone.
4. **Who answered lives in the transcript, not in the hook payload (d).** The `tool_result` line carries
   `permissionDecision.source` (`hook` or `user_temporary`) and, for a denial, `toolDenialKind` (`permission-rule` for a
   hook deny, `user-rejected` for a terminal No). No hook payload carries it.
5. **Timeouts.** The documented default hook timeout is 600 s; no maximum is documented. Neither was measured. The
   timeout behaviour itself (fallback to the dialog) was measured in C1.
6. **Questions (ADR-012 item 5).** `PermissionRequest` fires for `AskUserQuestion` (E1), but answering a question
   through it was not tried. A `PreToolUse` hook can answer a question through `updatedInput.answers` (E2), and the
   terminal then says the user answered, which misattributes the answer; `PreToolUse` also fails (b). No question
   decision route is proven.

## Decision

- **The hook route is not adopted yet; the keystroke exception stays** (`channel: 'hook-keystroke'`, ISSUE-134) for
  every OS and Claude Code version. ADR-012 item 1 decides per OS, and only macOS was measured.
- **Gate for ISSUE-135.** ISSUE-135 adopts `hook-decision` only when this record shows (a), (b) and (c) for the
  supported Claude Code versions on every OS. Today it shows them on macOS 26.6.2 with Claude Code 2.1.299 only, through
  `PermissionRequest`. A Windows 11 run is required before ISSUE-135 can rely on this record; Windows is not covered by
  any waiver. Linux falls under the owner's standing decision of 2026-10-10 that Linux manual runs are not blocking;
  whether that decision also covers adopting the hook route on Linux unmeasured is a decision for the lead and the
  owner. Until then, ISSUE-135 builds nothing that depends on the hook route.
- **If the hook route is adopted later, the event is `PermissionRequest`**, never `PreToolUse` (finding 2). The
  fixtures under `fixtures/claude/hooks/2.1.x/` are the payloads its contract tests replay (`17` §4).
- **Decisions this run raises, for the lead and the owner** (not taken here):
  - B2 asymmetry (finding 3): the hook route needs a way to learn that the terminal answered first, for example the
    transcript's `permissionDecision.source` (finding 4), before ADR-012 item 2's `answered-elsewhere` close can rely on
    it.
  - Questions (finding 6): until a question decision is proven on a route that meets (b), observed-Claude questions keep
    "Jump to terminal" only (ADR-012 item 5).
- A later run appends to this record: Windows 11 first, then Linux if the lead asks for it, and every newly supported
  Claude Code version.
